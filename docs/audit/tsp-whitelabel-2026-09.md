# White-label leak audit (TSP) — 2026-09

Orbetra is sold to TSPs who present the platform under **their** brand to **their** customers. Every
place our identity — the name Orbetra, `orbetra.com` / `orbetra.dev` / `dash.orbetra.com`, our marks,
our mail address — surfaces in front of a reseller's end customer is a route by which that customer
can find us and be served directly, cutting the reseller out. This audit swept every channel a
reseller's customer can reach (the SPA, e-mail, DNS, the public API surface, device hardware
configuration) for platform identity, and states for each leak **who** sees it and under **what
condition**. It covers only tenants holding the `whiteLabel` entitlement (all `tsp_*` plans); for
`direct_*` tenants our brand is correct and its appearance is not a finding.

**Method.** Six independent hostile auditors, one per channel (SPA shell/routing · outbound e-mail
identity · e-mail brand rendering · DNS and domain onboarding · API/HTTP surface · device onboarding
and storage/keys). Every raised finding then went to refuters instructed to kill it, each on a
distinct lens — **reachability** (can a reseller's customer actually get there?), **existing guard**
(is it already closed elsewhere in the code?), **accuracy** (is the quoted mechanism what the code
does?) — with a majority refute killing the finding outright.

That second pass changed the answer sheet substantially: **12 findings were refuted and killed, and
of the survivors 5 had their severity moved and 9 had a load-bearing sub-claim deleted as factually
wrong.** Several auditors independently reported the same defect from different call sites; those
were merged, so 18 confirmed reports condense to the **14 distinct defects** below. The ids are
stable and are what remediation must reference.

## W-1 — the platform console renders `Orbetra` on every reseller's domain

```tsx
// apps/web/src/components/ConsoleShell.tsx:69-77
<div className="text-sm font-semibold" style={{ color: 'var(--admin-ink)' }}>
  Orbetra
</div>
<div className="text-[11px] uppercase tracking-wider" …>{t('console.title')}</div>
```

```ts
// apps/web/src/router.tsx:345-350 — the only guard on the whole /platform tree
beforeLoad: async ({ location }) => {
  if (!(await hasSession())) { throw redirect({ to: '/login', search: { redirect: location.href } }) }
},
```

The route's own docblock states the intent — *"The route only checks for a session; the ROLE gate is
the server's"* — which protects the **data** and not the **brand**. The Caddy tenant block 404s six
platform API paths (`/v1/docs*`, `/v1/openapi.json`, `/v1/public/signup`, `/v1/public/pilot-request`,
`/v1/partner/*`, `/r/*`) but `/platform` is not an API path, so it falls through to
`handle { reverse_proxy web:5173 }` at `Caddyfile:220` and is served by the SPA on every reseller
domain.

The leak is the **shell**, not the data: of the seven console pages the two that do self-gate
(`app/platform.tsx:47`, `app/affiliates.tsx:54`) render their `denied` screen *inside* ConsoleShell,
so the wordmark and the full nav show on the refusal too. Four more (`users`, `billing`, `lapses`,
`errors`) print their `PageHeader` regardless of the 403 — `lapses.tsx:36` renders *"Overdue —
Customers behind on payment, and how close each is to losing their fleet"*. So a reseller's customer
does not merely see a stray word; they see an unmistakable vendor back-office and its business
vocabulary.

**Severity moved high → medium.** Nothing links there: the nav item is
`{ key: 'shell.console', to: '/platform', platformOnly: true }` (`AppShell.tsx:106`), filtered in both
the sidebar (`:345`) and the ⌘K palette (`:310`) by `role === 'platform_admin'`. The "stale bookmark"
argument was also killed — `grep -rn "app/platform|app/affiliates" apps/web/src` finds only the two
import lines, and those redirect routes always showed non-admins a denied screen, so no customer
holds those URLs. Reaching it requires an unusual action.

The one amplifier the auditors missed makes that action trivial for a *third party*:
`login.tsx:57-59` gives `?redirect` priority **over** role (*"An explicit `?redirect` still wins"*),
and `validateSearch` accepts any internal path. A pasted
`https://fleet.reseller.lt/login?redirect=/platform` delivers an ordinary customer, signing in with
ordinary credentials, straight into ConsoleShell under our name. Note the sidebar is `hidden … md:flex`,
so on a phone the leak is the page chrome and on a desktop it is the word itself.

*Dropped as unverified:* the claim that `/platform/anything` renders TanStack's default
`<p>Not Found</p>` *inside* ConsoleShell. `createRouter({ routeTree })` (`router.tsx:377`) passes no
options and no route in the file declares a `notFoundComponent`, so fuzzy resolution most likely
renders it at the root Outlet. Not load-bearing.

**Fix — two independent layers, both needed.** (a) Gate the tree on the role, not the session: in
`consoleRoute.beforeLoad`, after `hasSession()`, redirect to `/app` unless
`getCurrentUser()?.role === 'platform_admin'`, and apply the same to the `/app/platform` and
`/app/affiliates` redirect routes. (b) Make ConsoleShell brand-conditional, adopting the AppShell
pattern (`host?.whiteLabel === false ? PLATFORM_NAME : ''`, blank while the host is unresolved), so a
future routing regression cannot reprint the name. Belt and braces at the edge:
`handle /platform* { respond 404 }` in the tenant block — but note Caddy never sees `/app/platform`,
which the SPA resolves client-side, so the edge rule alone is not sufficient. `smoke.spec.ts:743`
already drives a non-platform user to `/app/affiliates → /platform/partners` and asserts the denied
body; extend it with `not.toContain('Orbetra')` on the shell.

## W-2 — signing out converts "brand unknown" into "this is the platform"

```ts
// apps/web/src/components/AppShell.tsx:296-297
forgetSessionBrand()
applyBranding(host?.branding ?? {}, host?.whiteLabel === true, false)
```

When `host` is `null`, `host?.whiteLabel === true` is `false`, so `applyBranding` runs the **platform**
branch: `document.title = branding.productName ?? (whiteLabel ? '' : PLATFORM_NAME)` (`branding.ts:408`,
`PLATFORM_NAME = 'Orbetra'` at `:437`) and `faviconLinks(undefined, false)` returns `DEFAULT_ICONS`
(`:468`) — `/platform-icon.ico`, `/platform-icon.svg`, `/icons/pwa-192.png`, our purple mark — injected
on the reseller's own domain.

This is the exact fail-open direction the rest of the brand code forbids. `publicBranding.ts:44-49`:
*"A FETCH FAILURE IS NOT THE PLATFORM … `null` means UNKNOWN, and every caller renders nothing
brand-specific for it (fail closed)."* The sibling effect twelve lines above was already corrected for
this class — `AppShell.tsx:188` is a bare `if (host === null) return`, whose comment names the same bug
— and the correction was not carried to the logout handler.

**What the victim actually sees.** With a warm cache (`primeBrandingFromCache` at `main.tsx:18` has
already painted the tenant's title and favicon from the host-keyed `orbetra.brand` entry) this is a
visible *swap* at the moment of clicking Sign out — their mark replaced by ours. And it **persists**:
the user lands on the login page, where AuthShell deliberately renders nothing brand-specific for an
unresolved brand, so our tab title and favicon become the only brand on that screen, until a manual
reload. With a cold cache the tab goes from carrying no identity at all (`index.html` ships no
`<title>` and no icon links) to reading literally `Orbetra`.

**Condition, precisely.** `host === null` at the moment of the click. Dominantly a failed
`GET /v1/branding` — `share.ts:47-55` returns `null` on any non-ok response or thrown fetch, and
`publicBranding.ts:76-80` caches the promise module-wide (`inFlight ??= …`), so one failure makes the
host `null` for the whole life of the page. It also covers the narrow case of a logout clicked while
the first fetch is still in flight.

**Fix.** Mirror line 188 at the call site — an unresolved host must leave the document untouched:

```ts
forgetSessionBrand()
if (host !== null) applyBranding(host.branding, host.whiteLabel, false)
```

Remove the `?? {}` / `=== true` pair rather than patching it; that pair *is* the encoding of
"unknown ⇒ platform". Line 207 carries the identical coercion and should be changed in the same pass
for consistency (it is not independently reachable by a reseller's customer — see **R-1** in Refuted).
Regression test next to `publicBranding.spec.ts`: a null host plus logout must not set
`document.title` to `PLATFORM_NAME` nor emit `DEFAULT_ICONS`.

## W-3 — every e-mail the platform sends carries our address in `From:`

```ts
// apps/worker/src/notify/emailTransport.ts:92
const from = env['MAIL_FROM']
// :150-155
await mailer.sendMail({
  from,
  ...(replyTo !== undefined && replyTo !== '' ? { replyTo } : {}),
  …
```

One process-wide sender for the entire worker, and the `EmailTransport.send` contract
(`drivers.ts:50`) has no `from` parameter — a per-tenant sender is not merely unconfigured, it is
**unrepresentable**. All three customer-facing producers converge here, from the single transport
built at `main.ts:208`:

- `authEmailWorker.ts:204` — activation / verify-email, password reset, "account already exists",
  lapse warnings. **This is the worst instance**: the activation mail is the first message a
  reseller's end user ever receives, arriving while they decide whether to trust a link. The
  surrounding code goes to deliberate lengths that the `From:` line then defeats —
  `authEmailWorker.ts:152-153`: *"a TSP's end user must not receive an Orbetra-branded mail naming
  their supplier."*
- `drivers.ts:58` — every overspeed / panic / geofence alert.
- `scheduledReporter.ts:218` — every scheduled report, whose recipients are free-text addresses an
  end customer's own `account_manager` typed in.

The bodies are fully white-labelled, which makes the sender line the only thing on the page that
names us. `Reply-To` masks it only for tenants who filled in `branding.supportEmail`; with that blank,
pressing Reply puts our address in the customer's `To:` field.

`docs/adr/036-tenant-sending-domain.md:3` — *"Status: **proposed** (2026-08-07) — decided, NOT yet
implemented. No `sesv2` code exists"* — and `:16-19` concedes the marketing claim *"Orbetra never
appears in-app or in emails to your end customers"* is currently false.

*Two sub-claims deleted as not code facts.* (1) "No display name is set, so phones show the bare
address": `MAIL_FROM` is passed verbatim to nodemailer, which accepts `Name <addr>`, so this is a
deployment string — and a configured one would read `Orbetra`, making the leak louder, not quieter.
(2) "SES derives Return-Path, DKIM `d=` and Message-ID from the same identity": nothing here sets an
envelope, and those depend on SES account configuration the repo does not pin. Assert only what the
code proves — the visible `From:` header.

**Fix.** Implement ADR-036: a per-tenant verified sending identity threaded through
`EmailTransport.send` as a `from` override, so the sender is a per-message argument rather than
closure state. **Carve-out for the implementer:** `job.kind === 'partner'`
(`authEmailWorker.ts:157-169`) deliberately sends unbranded from the platform — *"no supportEmail
override either: replies come to us, not to a reseller's support desk"*. A blanket per-tenant `From`
would dress our own affiliate notices in a reseller's identity and tell the partner which tenant they
are; that path must keep the platform identity. Interim, zero-cost mitigation: always set `Reply-To`
for white-label tenants, falling back to a tenant admin address rather than leaving it unset, and
surface "white-label tenant with no sending identity" as a visible setup gap in the branding UI.

## W-4 — "is this white-label?" is answered by counting JSON keys, not by the entitlement

```ts
// packages/shared/src/email.ts:198-201
const whiteLabel = Object.keys(branding).length > 0
const product = escapeHtml(whiteLabel ? branding.productName ?? tenantName : platform.name)
const logo = whiteLabel ? safeHttpsUrl(branding.logoUrl) : safeHttpsUrl(platform.logoUrl)
// :258 footer
`<p style="margin:0 0 4px">${product}${support}</p>`
```

A tenant holding the entitlement but with `branding = {}` takes the **platform** branch: the header
renders `Orbetra`, the footer repeats it, and `tenantName` — passed in by all six templates — is
discarded. The branch is deliberate and snapshot-tested (`apps/api/__tests__/email.spec.ts:20-30`,
*"EMPTY branding is not a white-label tenant"*), with the docblock at `email.ts:187-197` arguing that a
tenant with no branding *"is not a reseller"*. The defect is precisely that this proxy is wrong for a
`tsp_*` tenant.

Header is logo **or** wordmark, never both (`email.ts:213-216`). With `EMAIL_LOGO_URL` set it is
`<img src="https://orbetra.com/email-logo.png" alt="Orbetra">`; unset — the compose default,
`EMAIL_LOGO_URL: ${EMAIL_LOGO_URL:-}` at `docker-compose.apps.yml:83` — a styled `<span>` reading
`Orbetra`. Either way the customer sees the string (most clients block remote images and render the
alt), and the footer prints it a second time regardless.

Filing this at one call site understates it: `renderBrandedEmail(x.branding ?? {}, …)` is the identical
pattern in `notify/message.ts:89`, `verifyEmail.ts:80`, `passwordResetEmail.ts:79`,
`signupExistsEmail.ts:89`, `lapseEmail.ts:107` and `scheduledReporter.ts:133`, and
`authEmailWorker.ts:183` re-implements the same key-count test — reaching the activation subject line
and the plain-text signature too. **Fix once, at the renderer.**

*Condition, corrected.* The auditors' "every self-serve signup" is wrong: `signup.ts:79,260` hard-pins
`plan: 'direct_10'`, where our brand is correct. The real population is any tenant on a `tsp_*` plan
that has not yet saved a single branding field, reached by (a) `POST /v1/tenants` with `plan` omitted,
falling through to `schema.prisma:117 plan TenantPlan @default(tsp_grow)` beside
`:113 branding Json @default("{}")` — a sales-led reseller white-label-entitled and platform-branded
from minute one; and (b) an operating `direct_*` tenant upgraded to a TSP price via checkout or the
Stripe webhook, which flips the entitlement on a fleet that **already has** live alert rules and
end-customer users while branding stays `{}`. Path (b) is the sharp one: exposure begins with the next
alert e-mail to an existing customer, with no "no customers yet" window to hide behind.

*Limb deleted.* "Any stored branding failing `brandingReadSchema` reverts a configured reseller to our
brand" is refuted by `entities.ts:686-696`: every field is `.optional().catch(undefined)` and the
transform drops only the failed keys — *"drop the keys that failed, so `Object.keys(branding).length`
stays an honest 'what is set'"*. A bad field costs that field, not the brand. What survives is far
narrower: a reseller whose **only** stored field is invalid collapses to `{}`.

**Fix.** Pass the resolved `whiteLabel` entitlement into `renderBrandedEmail` and branch on it. When
true, the chain must be `productName → tenantName` and must never reach `platform.name` or
`platform.logoUrl`; the key count then only chooses between those two. `resolveRecipient`'s SQL must
start selecting the plan.

## W-5 — the zero-setup `<slug>.orbetra.com` becomes the tenant's permanent mail host

```sql
-- apps/worker/src/notify/tenantOrigin.ts:18-21, under the docblock
-- "The tenant's own host: the OLDEST verified domain, so the choice is stable as they add more."
SELECT domain FROM tenant_domains WHERE "tenantId" = $1 AND verified = true ORDER BY "createdAt" ASC LIMIT 1
```

```ts
// apps/api/src/routes/crud.ts:2424 — a subdomain of our own zone is verified on creation
db.tenantDomains.create(scopeOf(a), { userId: a.userId }, domain, newTxtToken(), ownZone ? { verified: true } : {})
// "verified on creation for our own zone: there is no ownership for the tenant to prove"
```

The onboarding order the product itself teaches — take the instant subdomain now, do DNS later —
therefore pins the platform subdomain as the mail host **forever**, because `createdAt` never changes.
Customers browse `track.reseller.lt` all day and then receive a password-reset mail whose visible link
text reads `https://reseller.orbetra.com/reset-password?token=…`. It hides well in QA because the page
that opens still renders correctly white-labelled: the subdomain is itself a verified tenant domain,
so pre-login branding resolves by Host. The leak is the hostname alone.

Scope is wider than password reset. `onTenantHost` also rewrites `verify-email` — the first mail a
reseller's new end user ever receives — and `signup-exists`; and `brandAssetOrigin`, which calls the
same `primaryDomain`, stamps the host onto the logo `<img src>` in `notifyWorker.ts:85` (alerts) and
`scheduledReporter.ts:173` (scheduled reports). Auth links are visible in **both** MIME parts
(`emailFallbackLink`, plus the plain-text `${s.button}: ${resetUrl}`), so nothing depends on a click.

Two extra conditions to state: the deployment must set `PLATFORM_DOMAIN` (README:106 — it requires a
published `*.orbetra.com` A record; unset ⇒ the option is never offered), and the reseller must still
hold the subdomain row. They *can* dislodge it by deleting that row, but nothing in the UI says mail
follows the oldest domain — the Domains card is a flat list with no primary concept.

The oldest-wins rule is pinned by `apps/worker/__tests__/verifyEmail.spec.ts:126-131` using
`first.reseller.lt` / `later.reseller.lt` — two of the tenant's **own** domains. Stability is correct
for that case; the platform-subdomain interaction is unconsidered, not deliberate.

**Fix.** Rank a domain outside `PLATFORM_DOMAIN` above one inside it, falling back to `createdAt` only
within each group — reuse the existing `isUnderPlatformDomain` predicate, e.g.
`ORDER BY (domain LIKE '%.' || $2) ASC, "createdAt" ASC LIMIT 1`. Better still, give the tenant an
explicit primary-domain choice in the Domains card.

## W-6 — an uploaded logo is served from our host when the tenant has no domain

```ts
// apps/worker/src/notify/tenantOrigin.ts:42-47
const domain = await primaryDomain(pool, tenantId)
if (domain !== null) return `https://${domain}`
if (appBaseUrl === undefined || appBaseUrl === '') return null
try { return new URL(appBaseUrl).origin }
```

The relative uploaded-asset path is made absolute against the **platform** origin, so a fully
white-labelled mail carries `<img src="https://app.orbetra.com/v1/public/brand/<hash>.png">`. The `alt`
is the product name, so a blocked image degrades safely — the leak is the URL and the request, not the
rendered fallback.

**Anchor is `:44-46`, not `:43`** (line 43 is the correct tenant-domain branch). Of the three callers,
`authEmailWorker.ts:195` should **not** be cited: when `host === null` that same mail's visible button
already points at `https://app.orbetra.com/…`, so the image adds no exposure, and ADR-041's recorded
acceptance reasons only about that case. The instances that matter are the two ADR-041 never
considered, because their mails contain **no URL at all**: `notifyWorker.ts:83-85` (alerts) and
`scheduledReporter.ts:170-173` (scheduled reports). On the report path `recipients: string[]` is a
free-text address list, so a recipient may have no user account and no other sight of our host
whatsoever.

Condition is narrower than first stated: it excludes `<slug>.orbetra.com` tenants, whose row is
created `verified: true`, so `primaryDomain` returns it and this fallback never fires. It also
requires `APP_BASE_URL` set in the worker, and an *uploaded* asset — `absolutizeBrandAssets`
(`brandAsset.ts:82-84`) only rewrites relative `/v1/public/brand/…` paths, leaving a tenant's own
`https://` URL untouched.

**Severity set to low.** Nothing in the rendered mail names our host, and the "remote-image prompt
names the origin" premise is unreliable (Gmail proxies through googleusercontent; Outlook and Apple
Mail prompt without naming the origin). Discoverable by inspection.

**Fix.** Return `null` rather than the platform origin when the tenant holds the `whiteLabel`
entitlement — `safeHttpsUrl` then drops the path and the header degrades to the styled product-name
wordmark, i.e. a missing logo rather than a vendor disclosure. Pair with a UI warning that the logo
will not appear in mail until a domain is verified. Worth fixing in the same pass:
`primaryDomain`'s `catch { return null }` (`:23`) makes a transient DB fault indistinguishable from
"no domain", so a blip stamps our host on a tenant that **does** have a custom domain.

## W-7 — an unresolved brand becomes `[Orbetra]` on a customer's lock screen

```ts
// apps/worker/src/notify/message.ts:55,59
const brand = ctx.brand && ctx.brand.trim() !== '' ? ctx.brand : 'Orbetra'
const subject = `[${brand}] ${title} — ${device}`
// apps/worker/src/notify/drivers.ts:119 — the same string, verbatim, as the push title
const payload = JSON.stringify({ title: msg.subject, body: msg.text })
```

Note the asymmetry that makes this a decision rather than an oversight: `apps/web/sw.ts` deliberately
falls back to a **brandless** title (`data.title ?? ''`, *"`'Orbetra'` there named the platform to
people who have never heard of it"*) — but that neutrality is only reachable on an unparseable
payload, because the server always supplies a title, and when it degrades it degrades to our name.

The blast radius is larger than the subject. `renderAlertHtml` passes `ctx.branding ?? {}`
(`message.ts:89`), so the same message takes W-4's platform branch: our wordmark (and our logo where
`EMAIL_LOGO_URL` is set) in the masthead, and `<title>[Orbetra] …</title>`. The computed `tenantName`
is dead on that path.

**Channel scope, corrected: Telegram is clean.** `drivers.ts:71` sends `text: msg.text` only, and
`text` (`message.ts:62`) is built from `s.alertHeading(title)` — no brand token in any of the four
locales. Only the e-mail subject, the e-mail shell and the web-push title leak. Web push additionally
requires VAPID keys (`drivers.ts:169`); e-mail has no such gate.

**The trigger must be differential**, which the auditors got wrong. `notifyWorker.ts:122` runs
`loadRuleChannels` on the same pool **first**, uncaught, so a plain DB outage throws and BullMQ
retries — nothing is sent, no leak. The leak needs query #1 to succeed while query #2 (the
devices⋈accounts⋈tenants join, which alone selects the newer columns `a."unitSpeed"`, `d.plate`,
`t.branding`) fails: a column-specific 42703, or an acquire timeout under pool exhaustion. The
deploy-ordering window is real but is operator deviation from a documented procedure —
`docs/runbooks/staging-app-deploy.md:7` already mandates *"Migrate BEFORE `up -d`, not after"* and
names this exact leak — though nothing in CI or compose enforces the order.

Also correct the example. On every stated trigger the **entire** context is lost, so the real output
is `[Orbetra] Overspeed — 356938035643809` (raw device id, UTC, English, metric), not a resolved
vehicle name. `Tenant.name` is non-nullable (`schema.prisma:109`), so "resolved device, unresolved
brand" is effectively unreachable. The raw-id form is if anything more alarming: our name attached to
a number the customer does not recognise.

**Fix.** Degrade brandless, not platform-branded: when `ctx.brand` is empty emit
`${title} — ${device}` with no bracket prefix, and pass no platform fallback into the shell. Update
the two pinning assertions — `notify.spec.ts:195` and `:283` (the Lithuanian case, easily missed). The
tenant id is already in hand at the call site (`notifyWorker.ts:127` reads `device:tenant` from Redis
in the same `Promise.all`), so a registry-backed brand is available without the query that failed.
Note the worker cannot distinguish `tsp_*` from `direct_*` on this path — the lookup that would tell
it is the one that failed — so brandless is the only safe default for both.

## Refuted — do not act on these, and do not re-raise them

Recorded with the reason, so the same false finding does not consume another audit in three months.

- **R-1 · The stale-closure brand write at `AppShell.tsx:202-213`.** The React defect is real — the
  effect has `[]` deps and captures `host` from the first render, when `usePublicBranding()` always
  returns `null`, so `applyBranding(b.branding, false)` writes the platform title/icons and poisons
  the `orbetra.brand` cache with `w:false`. It is not a leak, on three counts. `emitBrandingChange()`
  fires only from `routes/app/branding.tsx:112,131` after a **successful** save, and
  `PATCH /v1/tenant/branding` is gated by `if (!tenantWide(c)) return problem(c, 403, …)` plus
  `TENANT_ADMINS` — an account-scoped user (which every reseller's customer is) gets a 403 and nothing
  is emitted. The only person who can trigger it is the TSP's own tenant-wide admin, our direct
  contracting customer, in their own browser, and the cache is host-keyed and per-browser so it cannot
  travel. It also needs a navigate-away race (`beginBrandPreview()` is held for the page's lifetime and
  `applyBranding` short-circuits while it is), and it self-heals on the very next load, when
  `usePublicBranding` re-applies with `whiteLabel = true`. Fix the coercion for hygiene (W-2's fix
  should cover line 207 too); do not file it as a leak.
- **R-2 · `apps/web/public/dev-style.json` and the other platform-branded static files.** They are
  served from every tenant origin, confirmed. But nothing on a white-label host ever requests them:
  `/orbetra-logo.svg` is behind `host?.whiteLabel === false`, `/orbetra-wordmark.svg` behind the
  non-tenant AuthShell branch, `platform-icon.*` behind `branding.ts:468` (`return whiteLabel ? [] : DEFAULT_ICONS`),
  and a tenant manifest carries zero icons. `/dev-style.json` is fetched only when
  `VITE_MAPBOX_STYLE_*` point at it, which only the e2e harness does. The auto-fetched names
  (`/favicon.ico`, `/apple-touch-icon.png`) deliberately **do not exist** — that was the actual fix.
  Reaching any of these requires already knowing our name, so the file cannot disclose an identity, only
  confirm one the visitor holds. Adding static-path 404s would delete zero information while creating a
  denylist that must track `public/` forever.
- **R-3 · The `orbetra.*` localStorage keys and `orbetra:*` DOM events.** The strings exist, but the
  claimed condition is false: `applyTheme` and `primeBrandingFromCache` are pure **readers**
  (`primeBrandingFromCache` passes `remember = false`, *"a value that came OUT of the cache must not be
  written back into it"*), so on a genuine first visit none of the eight keys exists; seven are written
  only by a deliberate user action. No UI surface, export, error path or network payload renders a key
  or event name — seeing them requires DevTools, and the event names require `getEventListeners`. And at
  that depth the same bundle already ships `PLATFORM_NAME = 'Orbetra'` and `alt="Orbetra"` in plain
  text, so renaming twelve identifiers moves nobody from "does not know" to "knows".
  `orbetra.accountContext` is additionally mis-audienced: it is written only from TSP-admin surfaces.
- **R-4 · No ErrorBoundary anywhere in `apps/web`.** Verified absent (zero matches for
  `ErrorBoundary|componentDidCatch|errorComponent|notFoundComponent` across 134 files). But the
  framework defaults contain **no platform identity** — an unstyled `Something went wrong!` and
  `<p>Not Found</p>`. The claimed `document.title` interaction is wrong: `AppShell.tsx:188` guards on
  `host === null`, so during normal browsing on a tenant host the title is theirs or `''` and the
  favicon theirs or none — a crash freezes a **neutral** tab. A real UX/robustness gap; file it as UX,
  not as a leak.
- **R-5 · Auth links land on the platform host for a tenant with no verified domain.** Structurally
  self-neutralising: `primaryDomain`'s predicate (`verified = true`) is the same one Caddy's
  on-demand-TLS gate reads (`caddyAsk.ts`: *"Caddy mints a cert iff 200"*), so in that state the tenant
  has **no working host of their own**. Their customers can only reach the app on the platform host —
  where `/v1/branding` returns `whiteLabel: false` by design — so the mail names the origin the
  recipient already has in their address bar. The activation-mail limb is also factually wrong:
  reseller-created users are verified on creation (`users.ts:61 emailVerifiedAt: new Date()`,
  *"Only PUBLIC self-serve signup mints an unverified user"*), so they never receive one.
- **R-6 · The config SMS embeds a platform-wide hostname (`packages/shared/src/onboarding.ts`).** The
  quoted mechanics are the **guard**, not the defect: `SAFE_HOST` + null-guarded builders + a rendered
  gap + a test asserting no `orbetra` string. The load-bearing claim — "the code supports no
  white-label-safe alternative" — is false: white-label safety needs a brand-**neutral** hostname, not a
  per-tenant one, and `SAFE_HOST` accepts any hostname or bare IP (the hardware runbook uses
  `185.80.129.33`). Following it would build per-tenant ingest DNS for a raw-TCP endpoint to solve what
  one env value solves. The residual — nothing tells the operator to choose a neutral value — is
  recorded as **W-14**.
- **R-7 · `POST /v1/auth/forgot-password` builds reset links from `APP_BASE_URL`.** Refuted three times
  on the same reading error: `on()` **is** the rewrite. `authEmailWorker.ts:189-190` resolves
  `primaryDomain` and binds `onTenantHost`, which swaps protocol and host outright. The docblock at
  `:73-88` names this exact leak as the reason the function exists (*"a VrummTrack-branded
  password-reset mail sent its user to dash.orbetra.com"*), and `verifyEmail.spec.ts:121-131` pins it.
  The API deliberately builds a placeholder origin so the host lookup stays **off** the request path,
  where a per-tenant query would reintroduce the timing signal the enumeration defense removes. (What
  host is chosen when a tenant holds several is a real defect — that is **W-5**.)
- **R-8 · The `orb_live_` API-key prefix.** All three key routes open with
  `if (!admin(c)) return problem(c, 403, 'Forbidden')` against `TENANT_ADMINS`, so `account_manager` and
  `viewer` — the only roles a reseller's account invite offers — get 403 on list, create and revoke, and
  the audit trail that stores the prefix is tenant-wide-admin-only. The audience is the reseller himself
  and us. Reaching an end customer requires the reseller to hand over plaintext out of band, and the
  string handed over is `orb_` — a three-letter abbreviation, not the vendor name, in a form
  (`sk_live_`, `ghp_`) that carries no attribution.
- **R-9 · The `orb_refresh` cookie.** `httpOnly: true`, `sameSite: 'Strict'`, `path: '/v1/auth'`, no
  `domain` — page JS cannot read it, `apps/web` has no cookie banner and no legal/cookies route, and the
  only mentions under `apps/web/src` are comments. It is reachable solely via DevTools → Application, and
  `orb` does not identify a vendor to anyone who does not already know the answer. Filing it beside the
  genuine `orbetra.*` string leaks would dilute them.
- **R-10 · `iss: 'orbetra-api'` in every access token.** The token is never at rest: `auth.ts:11`
  keeps it in module memory only (*"XSS cannot read what is never stored"*), it is sent as a header
  only, and the sole token in any URL is the WS ticket, which is opaque CSPRNG by explicit rule. The
  "integrator" half is simply wrong — programmatic consumers authenticate with `X-Api-Key`, never a JWT.
  Extraction requires DevTools plus copying an Authorization header plus base64-decoding, with no
  shortcut past any step.
- **R-11 · `<slug>.orbetra.com` puts our domain in the customer's address bar, and the Add-domain form
  defaults to it.** This is a priced, disclosed product option, not a leak. There is exactly one
  creation call site (`crud.ts:2424`, entitlement-gated and tenant-wide-admin-only) with no
  auto-provisioning anywhere, and the form states both the hostname and the consequence in all four
  languages: the radio reads *"Subdomain on orbetra.com (instant)"*, the slug box is suffixed
  `.{platformDomain}`, and the note underneath says *"Your customers sign in here."* The pre-selected
  radio discloses nothing by itself and submits nothing (submit is disabled until a slug is typed);
  "My own domain" is one click away. No fix exists that keeps the feature — the suffix **is** our zone,
  which is exactly why the row can be created `verified: true`. Reporting it sends someone to un-ship a
  founder-chosen capability.
- **R-12 · The Caddy tenant denylist has no rule for static paths.** Same refutation as R-2, from the
  edge side: every branded file is behind a `whiteLabel === false` render branch, nothing auto-requests
  them, and the JS bundle — byte-identical on every host — already ships `PLATFORM_NAME = 'Orbetra'` in
  plaintext, which is *how* someone would learn the filenames to guess. A per-filename edge denylist
  would be false comfort with a permanent maintenance cost.

## What resisted attack (worth keeping)

Every pre-cleared guard held under a second look, and the pattern in them is worth naming: each is a
place where **unknown fails closed** rather than resolving to the platform. `AuthShell` renders nothing
for an unresolved brand; `faviconLinks` returns `[]` rather than our icons for a white-label host with
no image; the PWA manifest emits no icons for a tenant rather than falling back to ours;
`INGEST_PUBLIC_HOST` renders a visible gap rather than a substitute; `/favicon.ico` and
`/apple-touch-icon.png` were **deleted** rather than gated, because a browser requests them before any
JavaScript runs. `brandingReadSchema`'s per-field `.catch(undefined)` is the same instinct applied to
data: one bad field costs that field, not the tenant's whole identity.

Almost every confirmed finding above is the same rule broken in the same direction — `?? {}`,
`=== true` on a nullable, `Object.keys(...).length > 0`, `?? 'Orbetra'`. **Three of the four highs
(W-3, W-4, W-7 with W-8) are a missing or mis-derived white-label signal**, not a missing check. The
durable fix is to make the entitlement an explicit argument on every render and send path, so
"unknown" cannot be spelled as "ours".
