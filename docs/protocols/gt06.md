## 1. What speaks this protocol

**VERIFIED (rank 1 + rank 2 + rank 3).** GT06 is not one protocol; it is a *brand-shaped family* of
mutually incompatible dialects that share an envelope. There is no version field on the wire.

### 1.1 The vendor line

Shenzhen Concox Information Technology, now trading as **Jimi IoT**. The GT06 envelope is used by,
at minimum:

### 1.2 What is **not** GT06 even though it wears the badge

**VERIFIED (rank 3).** `JC181, JC371, JC450, VG502, JM-VL502` are **jt808**, not GT06. jt808 allocates
6 bytes for the device identifier, so those platforms ident with **14 digits of the IMEI, not 15**.
Rejecting a device that never sends a `7878`/`7979` header is the correct response, not a bug.
Source: <https://flespi.com/protocols/concox>.

### 1.3 Firmware ranges — there is no version negotiation

**VERIFIED.** The protocol carries no version field. Three firmware-visible discriminators exist,
in descending order of usefulness:

1. **The build string**, protocol **0xFD** (and some 0x21 text replies), e.g.
   `[VERSION]GT06D_20_60DM2_B25E_V15_WM[BUILD]2013/12/28 15:24` — VERIFIED in the corpus
   (three consecutive frames, serials 0x002A/0x002D/0x0030, all CRC-PASS). Traccar has no constant
   for 0xFD and discards it. **Capture and persist it per device: it is the only honest in-band
   answer to "which dialect is this".**
2. **The login type-identifier word** (bytes 8–9 of a LEN-0x11 login): `0x100B` GT07, `0x100F`,
   `0x7000` LL301, `0xA001`. INFERRED as a model code — no vendor publishes the enumeration.
3. **The JC400 marker** `FF FF` at payload offset 0 of protocol 0x95 — VERIFIED, and the *only*
   in-band variant marker in the entire family that does not depend on the length byte.

Everything else requires an operator-set model string. See §7 Trap 14.

### 1.4 Coverage estimate

**INFERRED.** Traccar's decoder — the widest implementation in existence — declares 87 protocol-number
constants and 16 variants, and its own author's summary is *"there is a million different variations"*
(<https://www.traccar.org/forums/topic/gt06-data-not-translated-correctly/>). A decoder built to this
document covers: **every packet a classic GT06/GT06N/GT07/GT02D emits**, the modern LL301/VL0x
2G+4G location/alarm/heartbeat set, the 0x94 information channel, the TLV module channel, and the
0x8C OBD channel. It does **not** cover: media transfer (0x35/0x36/0x41/0x8D), the 0x8E CAN packet
(spec-only, no sample exists anywhere), and the eight wire-indistinguishable OEM dialects.

## 2. Transport and session

### 2.1 Transport

| Property | Value | Label |
|---|---|---|
| Transport | **TCP only.** Traccar registers `new TrackerServer(config, "gt06", false)` — third argument is `datagram` | VERIFIED (rank 2, `Gt06Protocol.java`) |
| UDP | No vendor doc mentions datagrams. Devices expose a UDP setting that reportedly does nothing | UNKNOWN — see §9 Q6 |
| Port | 5023 is *Traccar's* convention, not the protocol's. Devices are pointed with SMS `SERVER,<mode>,<host>,<port>#` | VERIFIED (rank 2/5) |
| Session model | One long-lived TCP connection per device. **Identity is bound to the socket by the login packet; every later frame is anonymous** | VERIFIED (rank 1 §5.1 + rank 2 `getDeviceSession`) |
| Stream shape | Multiple frames per segment, frames split across segments | VERIFIED — corpus vector `7979005bfd…` is three complete 97-byte frames concatenated, interior `7979` headers at offsets 97 and 194, all three CRC-PASS |

### 2.2 Frame envelope — VERIFIED (v1.8.1 §4.1–4.7; JM-LL301 §1; v1.9.0 §4)

```
SHORT:  78 78 | LEN(1)     | TYPE(1) | PAYLOAD(N) | SERIAL(2) | CRC(2) | 0D 0A     total = 5 + LEN
LONG:   79 79 | LEN(2, BE) | TYPE(1) | PAYLOAD(N) | SERIAL(2) | CRC(2) | 0D 0A     total = 6 + LEN

LEN = 1 (TYPE) + N (PAYLOAD) + 2 (SERIAL) + 2 (CRC)
```

Vendor wording, verbatim (JM-LL301 §4): *"Length = Protocol number + Information content +
Information SN + CRC"*. **All multi-byte fields are big-endian, without exception.**

Max short frame 260 B. Max long frame 65 541 B — cap it (Traccar caps at 32 KiB); see §7 Trap 24.

**Form C — the hybrid.** VERIFIED (v1.8.1 §5.3.3.2, p.21): a `78 78` header with a **two-byte**
length exists for exactly one protocol number, **0x97** (English address reply, server→device):
`78 78 00 E9 97 …`, with the vendor stating *"only the length of data bit corresponding to the
protocol number of response address information is changed into two bytes"*. Modern docs
(LL301 §12c/§15c) replaced it with `79 79 00 BC 97 …`. **Never infer the length width from the
header alone when TYPE == 0x97.**

### 2.3 CRC — named, exactly

**VERIFIED.** The vendors call it "CRC-ITU". It is **CRC-16/X-25**:

| Parameter | Value |
|---|---|
| Polynomial | `0x1021` (normal) / **`0x8408` reflected** |
| Init | `0xFFFF` |
| RefIn | true |
| RefOut | true |
| XorOut | `0xFFFF` (i.e. final one's-complement) |
| Width | 16 |
| Check (`"123456789"`) | `0x906E` |
| **Span** | **from the first LENGTH byte through the last SERIAL byte, inclusive** — i.e. `bytes[2 .. n-5]` for both header widths |

Vendor text verbatim (v1.8.1 §4.6): *"from the Packet Length to the Information Serial Number
(including 'Packet Length' and 'Information Serial Number')"*. The Appendix A reference C is
`fcs = 0xffff; fcs = (fcs>>8) ^ crctab16[(fcs ^ *p) & 0xff]; return ~fcs;` with `table[1] = 0x1189`
and `table[128] = 0x8408` — the reflected form. Identical span for `7979` frames: **both** length
bytes are covered (VERIFIED on the 193-byte `7979 00BB 97 … 0016 8EA5` example — I computed 0x8EA5).

Reference implementation (bit-serial, no table needed):

```
crc = 0xFFFF
for each byte b in span:
    crc ^= b
    repeat 8 times:
        crc = (crc >> 1) ^ 0x8408  if (crc & 1)  else  (crc >> 1)
return (~crc) & 0xFFFF
```

Regression vectors I re-derived (every one matches a printed vendor value):

| Span bytes | CRC |
|---|---|
| `05 01 00 01` | `D9DC` |
| `05 01 00 02` | `EB47` |
| `05 01 00 05` | `9FF8` |
| `05 13 00 1F` | `100E` |
| `05 27 00 1C` | `C75A` |
| `05 26 00 1C` | `9D86` |
| `0D 01 0123456789012345 0001` | `8CDD` |

**Vendor rule (all four PDFs): a CRC mismatch means silently discard the packet.** JM-LL301, on
every packet table: *"If the receiver receives a packet that contains a CRC error, it ignores the
error and discards the packet."*

**Traccar does not do this.** `Checksum` is referenced exactly once in `Gt06ProtocolDecoder.java`,
inside `sendResponse()` — outbound only. `Gt06FrameDecoder.java` does not reference it at all.
That is why 28 of its own 183 test frames fail CRC. See §7 Trap 26.

### 2.4 The framer — the only algorithm that survives the corpus

Two facts fight each other:

* **The length byte lies on real firmware.** VERIFIED: Concox TK200 status packets under-declare by 2
  and compute the CRC over the wrong length byte, so the frame is *self-consistently* invalid:
  `78780813460602000204c6ffde0d0a` — 15 bytes on the wire, LEN 0x08 implies 13, and the CRC
  **passes as transmitted** (I recomputed 0xFFDE). Second instance, same device:
  `787808134606020002044dc5050d0a` → 0xC505, also passes.
  Tananaev's diagnosis: *"Message reports length 8, but the actual length is 10. Looks like the
  problem is on the device side."* (<https://github.com/traccar/traccar/issues/1727>). The vendor's
  own v1.8.1 §5.4.3 example reproduces the defect (`78 78 08 13 4B 04 03 00 01 00 11 06 1F 0D 0A`)
  *and* prints a bogus CRC — it fails both the LEN 0x08 reading (calc 0xF8B5) and the corrected
  LEN 0x0A reading (calc 0x634F).
* **`0D 0A` occurs inside real payloads.** VERIFIED, all three CRC-PASS with the interior CRLF
  inside the CRC span:

  | Frame | Interior CRLF | Content |
  |---|---|---|
  | `797900109b0344373532304136320d0a000f87f00d0a` | body off. 9 | 0x9B passthrough `D7520A62\r\n` |
  | `7979000e9b0332382e33a1e60d0a0289be490d0a` | body off. 7 | 0x9B `28.3` + GB2312 `℃` + CRLF |
  | `79790019941b524649443a3030384642324245424133390d0a000c14930d0a` | body off. 18 | 0x94/0x1B `RFID:008FB2BEBA39\r\n` |

So neither pure length-framing nor pure CRLF-scanning works. **CRC is the frame arbiter.**

```
FRAME(buffer):
  1. need >= 5 bytes. hdr = u16be(buf[0..1]).
     if hdr not in {0x7878, 0x7979}: resync — scan forward for the next 7878|7979,
     increment ingest_frame_resync_total, and continue.

  2. type = buf[3] (short) or buf[4] (long).
     ---- ORDER MATTERS ---- if type in {0x17, 0x69} attempt the SERIAL-LESS WALK (2.6) FIRST.
     Only if that walk fails do you fall through to step 3.

  3. declared = 5 + buf[2]              (short)
              = 6 + u16be(buf[2..3])    (long)
     Reject declared < 10 for non-{0x17,0x69} types — a runt `787801080d0a` exists in the corpus
     and drives Traccar to emit an ACK whose "serial" is the header bytes 0x7878.

  4. candidate A = declared. ACCEPT A iff  buf[A-2..A-1] == 0D 0A
                                    AND   crc_x25(buf[2 .. A-5]) == u16be(buf[A-4..A-3]).

  5. if A fails: scan for the first 0D 0A at index >= 9; candidate B = idx + 2;
     accept B under the same two tests; repeat to the next CRLF while B fails and
     B <= 260 (short) / cap (long).

  6. if nothing validates: drop the connection, count it. NEVER ACK an unvalidated frame.
```

Note that step 5 is what rescues the TK200 length lie (the true 15-byte frame CRC-validates), and
step 4 is what protects the embedded-CRLF frames (their declared length is correct, so the scan is
never reached). Traccar has the same ordering and is correct here — the claim that its CRLF fallback
mis-splits the 0x9B frames is false; I checked all four embedded-CRLF frames and every one has
`declared == actual` and a passing CRC, so the fallback never fires.

### 2.5 Resync budget

**INFERRED.** After N consecutive resyncs on one connection (N = 4 is a reasonable start), close the
socket. A device that has desynchronised will re-login and recover; a server that keeps scanning will
emit garbage positions. Always emit a metric — silent recovery hides a misbehaving firmware.
Field evidence: *"sending in between few strings which are not starting by 7878 or 7979. After that
server has stopped responding to the genuine pings also"*
(<https://www.traccar.org/forums/topic/gt06-protocol-issue/>).

### 2.6 The sub-family with no envelope at all

**VERIFIED (rank 2 + rank 5 capture; no vendor doc describes it).** For protocol numbers **0x17 and
0x69** in the WiFi/LBS-scan shape, the length slot is **the WiFi AP count**, and the frame carries
**no serial and no CRC**:

```
78 78 | APCOUNT(1) | TYPE(1) | BCD time(6) | AP[MAC 6 + RSSI 1] × APCOUNT
      | CELLCOUNT(1) | MCC(2) | MNC(1) | CELL[LAC 2 + CID 2 + RSSI 1] × CELLCOUNT | 00 | 0D 0A
```

Full structural decode of a live 2026 capture (traccar#5841, German device):
`78780017 260405214936 05 0106 03 3cc8d8c36e 3cc8d8c16e 3cc8d9926e 3cc8d5676e 3cc8d56e6e 00 0d0a`
→ 42 bytes, 0 APs, 2026-04-05 21:49:36, 5 cells, MCC 262 (DE) MNC 3, LAC 15560. Declared "length"
0x00. Note the **time here is BCD**, unlike every other packet in the family. The trailing `00`
before CRLF is **UNKNOWN** (§9 Q2).

Traccar answers these with a bespoke, CRC-less `78 78 00 <type> <the same 6 BCD time bytes> 0D 0A`
(`787800172604052149360d0a` in that log). Whether the reply is required at all is **UNKNOWN** (§9 Q3).

**Measured:** 11 of the 12 unique 0x17/0x69 frames in the corpus declare LEN of 0x00, 0x03 or 0x08
on real frames of 26–107 bytes. A framer that applies "reject LEN < 5" before reading the type byte
**deletes this entire sub-family** — and it is the fallback position source when GPS is unavailable
(underground parking, urban canyon, a concealed tracker in a stolen vehicle). Both shapes of 0x17
coexist: one corpus 0x17 declares LEN 0x28 and *is* a normally framed 45-byte LBS address request.
Hence the type-first ordering in step 2.

### 2.7 Login (0x01) — VERIFIED

| Off | Len | Field | Notes |
|---|---|---|---|
| 0 | 8 | Terminal ID | BCD, 16 nibbles. A 15-digit IMEI is **left-padded with one `0` nibble** — drop the leading nibble. `0864717003283581` → `864717003283581` |
| 8 | 2 | Type identifier | Model code. **Present only when LEN ≥ 0x11** |
| 10 | 2 | Time zone / language | see below |

Exactly two lengths exist in the wild, both CRC-verified in the corpus:
**LEN 0x0D** (18-byte frame, ID only) and **LEN 0x11** (22-byte frame, ID + type + tz).
**Branch on `LEN > 0x0D`, never on model.**

**Time-zone word** (JM-LL301 §2; GT07 §5.1.1.3) — VERIFIED as *packed decimal HHMM*:

```
value   = word >> 4          # a DECIMAL HHMM number: 800 => 8:00, 530 => 5:30, 1245 => 12:45
hours   = value / 100
minutes = value % 100
west    = (word & 0x0008) != 0      # bit 3: 1 => West (negate)
lang    = word & 0x0003             # 1 = Chinese, 2 = English
```

Verified east: corpus login `…0752533678900242 7000 3201 0005 1279` → 0x320 = 800 → **UTC+8:00**,
Chinese. Verified west: `…0864717003664467 100F 190A 0002 C6D2` → 0x190 = 400, bit3 set →
**UTC−4:00**, English. The vendor's own illustration is 0x4DD8 → 1245 → GMT−12:45 (and the PDF's
arithmetic misprints 1245 as "1246").

**Caveat that the label hides:** both *real* captures are whole-hour zones, which the wrong reading
(hours×100) also decodes correctly. The HHMM reading is confirmed only by a vendor illustration of a
zone that does not exist on Earth. See §9 Q8 — the half-hour zones (+5:30, +5:45, +12:45) are where
an 18-minute error hides.

### 2.8 The ACK contract, as rules

```
ACK(frame) = 78 78 | 05 | <TYPE copied verbatim from the frame>
                        | <SERIAL copied verbatim from bytes[n-6 .. n-5]>
                        | <crc_x25 of those 4 bytes> | 0D 0A          (10 bytes total)
```

**R1. The protocol number in the reply equals the protocol number in the request.** VERIFIED —
v1.8.1 §5.1.2: *"the protocol number in the response packet is identical to the protocol number in
the data packet sent by the terminal."*
*Exception, CRC-proven:* JM-LL301 §12's table row claims the reply to 0x27 is typed **0x26**, but its
own printed example is `78 78 05 27 00 1C C7 5A 0D 0A`. I computed CRC over `05 27 00 1C` = **0xC75A**
(matches) and over `05 26 00 1C` = **0x9D86** (does not). **The example wins: reply 0x27 to 0x27.**

**R2. Take the serial by absolute offset from the end** — `bytes[n-6 .. n-5]` — never by parse
position and never from the declared length. This is precisely the bug that made Traccar answer
serial `0002` to a TK200 frame whose serial was `04C6`, costing that device 15 minutes of silence
every 5 minutes. VERIFIED (traccar#1727 + commit `e2e050187`).

**R3. Never ACK a frame that failed CRC or framing.**

**R4. Never ACK a server→device type** (0x80, 0x81, 0x82, 0x97, address replies).

**R5. ACK only after the record is durably queued, and within the 5-second budget, from a
non-blocking path.** The ACK deadline applies to the whole path; a 6-second stall (a slow XADD, a GC
pause, a blocking DB write) flips the device into buffering mode and costs a TCP reconnect plus a
full login round trip.

**R6. Emit the ACK from the socket thread.** Traccar emits the ACK inside the protocol decoder and
returns the Position afterwards — it acknowledges *before* persistence. Do not copy that.

#### 2.8.1 What the acknowledged value MEANS to the device — read this twice

**The ACK is a liveness token for the link. It is not a delivery receipt for the record.**

No vendor document defines per-record retransmission keyed on the ACK, with exactly **two**
exceptions:

* **0x2D** — JM-LL301 §6, verbatim: *"If the protocol number is '0x2D', then it is a location packet
  that requires a response; if the server doesn't respond, then a backup action will be performed."*
  Field map identical to 0x22. What "backup action" means is **UNKNOWN** (§9 Q4).
* **0x8D large-file chunks** — the server replies 0x8D carrying a 1-byte **receive status flag**
  (`0x00` received, `0x01` receive error). This is the only per-unit success/failure signal in the
  protocol.

Everything else is **fire-and-forget**. A 0x22 record lost between the socket and durable storage is
lost permanently: the device considers a buffered record delivered the moment `write()` returns on
its socket, and nothing in the protocol lets it learn otherwise.

Consequences you must design for:

1. **The serial number is not an idempotency key.** VERIFIED, v1.8.1 §4.5: *"The serial number of the
   first GPRS data sent after booting is '1', and … automatically added '1'."* It is per-**boot**,
   wraps at 0xFFFF, and repeats after every reboot. Worse, genuine duplicates arrive with *different*
   serials — traccar#5460 contains two frames identical in every byte including the timestamp,
   differing only in serial (0x3C81 / 0x3C80) and CRC. Both CRC-PASS (I verified 0xD7AC and 0xC625).
   **Deduplicate on `(device_id, device_time, lat, lon)`, never on serial.**
2. **A wrong ACK has two different failure modes.** Sometimes the device retransmits until it sees
   its own serial (traccar#3704: request serials 0053/0054/0055 answered 0003/0004/0005 →
   *"Device keeps sending same data package until it receives confirmation with their Serial
   number… It can work correct sometimes but not always"*). Sometimes it goes **quiet for a fixed
   penalty interval** instead (traccar#1727: 5 minutes of data, 15 minutes of silence, forever).
   Design for both.
3. **Echo enforcement varies by firmware.** Two counter-examples: `vondraussen/gt06` hard-codes
   `78 78 05 FF 00 01 …` and patches only the type byte, and it works in production; JM-LL301 §4b's
   own heartbeat return example carries serial 0x0100 against a request serial of 0x0008 and still
   CRC-verifies (I confirmed 0x670E). **Echo it anyway — it is free and the spec demands it.**

#### 2.8.2 Who must be answered

| Type | Reply | Label / source |
|---|---|---|
| 0x01 login | **Required**, echo serial | VERIFIED — v1.8.1 §5.1.2 |
| 0x13 / 0x23 / 0x36 heartbeat | **Required**, echo serial | VERIFIED — v1.8.1 §5.4.2; LL301 §4/§5 |
| 0x8A time request | **Required** — `78 78 0B 8A YY MM DD hh mm ss <serial> <crc> 0D0A`, **plain binary not BCD**, **UTC** | VERIFIED — LL301 §3, example `78780B8A0F0C1D0000150006F0860D0A` CRC 0xF086 ✓ |
| 0x27 / 0xA4 alarm | **Required** — reply 0x27 / 0xA4 (see R1 exception) — **unless the alarm's language byte is `0x00`**, which LL301 defines as *"No reply from the platform is required"* | VERIFIED |
| 0x19 / 0xA5 LBS alarm | Reply required; **reply type is UNKNOWN** — LL301 §17b says 0x26, no CRC-checkable example exists in either direction | §9 Q9 |
| 0x22, 0xA0, 0x28, 0xA1, 0x2C, 0xA2, 0x94 | LL301 says *"No return packet is required."* GT06F says *"Location packet server no response"* for 0x12 and *"Server no Response"* for 0x94 | **Contested — see below** |
| 0x2A / 0x17 / 0xA7 address request | Reply 0x17 (short frame, **1-byte** inner length) for Chinese; 0x97 (`7979`, **2-byte** inner length) for English | VERIFIED from both vendor examples |
| 0x80 / 0x81 / 0x82 | Never ACK | VERIFIED |

**The contested row is the important one.** LL301's *"no return packet is required"* is one model's
PDF generalised to the whole family, and it governs the highest-frequency packet in the protocol.
Traccar does the opposite: its generic tail
`sendResponse(channel, false, type, buf.getShort(buf.writerIndex() - 6), null)` fires for the 0x22
class and for anything unhandled that is not a command — i.e. the largest deployed GT06 server in
the world ACKs these.

The costs are wildly asymmetric. ACKing unnecessarily costs **10 bytes of metered GPRS per fix**.
Not ACKing when the firmware expects it costs, by §2.9's own ladder: link declared abnormal at 5 s,
GPS retransmission enabled, TCP dropped, reconnect, re-login, and after three consecutive timeouts a
timed restart in 10 minutes — and it looks like a hardware or carrier fault, not a server bug.

**Rule: make it a per-model flag whose default is ACK.** Bytes are cheap; reboot loops are not.

### 2.9 Failure ladder and its cost

| Rule | v1.8.1 / JC100 | GT07 v1.4 | LL301 |
|---|---|---|---|
| ACK deadline | **5 s** | **10 s** | **5 s** |
| First status packet | after 3 min | after 5 min | timed |
| Timeout consequence | link "abnormal" → enable GPS retransmission, drop TCP, reconnect, re-login | *"activate the GPS data backup function"* | *"continue to send login packets"* |
| 3 consecutive timeouts | timed restart in **10 min** | 10 min | timed restart |
| 3 failed TCP connects | timed restart in **20 min** | 20 min | — |
| 5 unanswered heartbeats (JC100) | reboot GPRS stack, **max once per day** | — | — |

**Design to 5 s.** Three of four rank-1 docs say 5 s; designing to GT07's 10 s silently fails on the
other three families. (One rank-6 page claims 30–60 s — ignore it.) Note also that v1.8.1's own data-
flow diagram labels the same edge *"fail to receive response from the server within 5min"* — an
authoring slip; the prose is repeated verbatim in JC100 and LL301, so the prose wins.

**Unregistered IMEIs.** v1.8.1 §III.7: *"For the terminal which doesn't register an IMEI number, the
server will reply the terminal with a login request response and heartbeat packet response, rather
than directly disconnect the connection. (If the connection is directly disconnected or the server
doesn't reply … it will lead to a continuous reconnected by the terminal and the GPRS traffic will be
consumed heavily."* GT07 §5 says the opposite. **Follow v1.8.1**: ACK the login for an unknown IMEI,
store nothing, close after a short grace, and rate-limit. Traccar follows GT07, which is exactly why
unprovisioned GT06 units hammer public Traccar installs — and on our platform the customer pays for
that SIM.

### 2.10 Buffered / offline flush

* **Trigger:** ACK timeout (§2.9) or loss of GPRS. Named *"retransmission function for GPS tracking
  data"* (v1.8.1 §III.3) and *"GPS data backup function"* (GT07 §3).
* **Flush:** VERIFIED, LL301 §6/§7 — *"After the connection is established and there are cache fixes,
  the terminal will upload these cache fixes"* — as ordinary location frames in the same envelope,
  immediately after login, interleaved with live fixes.
* **The flush is NOT chronological.** VERIFIED (rank 5): a reporter observed records arriving
  06:08:45 UTC (live), then 02:57:19, then 02:57:23 — the device sent a fresh fix first and *then*
  flushed the backlog. Never assume monotonic time on a device shard; stitch trips by device time,
  not arrival time.
* **Two markers exist on 0x22/0xA0 and later types, never on legacy 0x12/0x16:**
  * **GPS data re-upload** (1 B): `0x00` real-time, `0x01` re-upload. Vendor notes it is
    *"unavailable on GT06"* — legacy models omit the byte entirely.
  * **Data upload mode** (1 B), LL301 §A0 / JC100 §5.3.1.15 — the enumeration is in §5.4.
    `0x05` = *"Upload the last valid fix prior to reconnection from a network interruption"*;
    `0x04`, `0x0A`, `0x0D`, `0x0E` are all "stale position while still".
* **Pipeline rule:** a record whose upload mode ∈ {0x04, 0x05, 0x0A, 0x0D, 0x0E} or whose re-upload
  flag is 0x01 is **history, not news**. It must not raise real-time alerts (overspeed, geofence) and
  must not advance trip distance.

### 2.11 Session identity, takeover, and restart

**VERIFIED (rank 2 + rank 5).** The IMEI appears only in the 0x01 login (and, oddly, inside three
packet types — 0x61, and 0x12/0x25 on QH302R/NT models). Consequences:

1. After any ingest restart, every device with an open socket keeps sending anonymous frames that
   cannot be attributed. They are dropped un-ACKed until the device's own timeout forces a reconnect.
   **Budget for a login storm on every deploy.**
2. Devices are observed *"opening a second channel while the first channel is still active"*
   (<https://www.traccar.org/forums/topic/gt06-protocol-issue/>). Per-IMEI takeover must be explicit —
   **last login wins, close the older socket** — never two half-alive sessions writing to one shard.
3. Never enable a "ignore session cache" style option: GT06 devices *"stop updating … because they
   don't send IMEI information in every message."*

## 3. Packet catalogue

### 3.1 The common GPS block — 18 bytes, VERIFIED

Identical in 0x10, 0x12, 0x16, 0x1A, 0x22, 0x26, 0x27, 0x2A, 0x2D, 0xA0, 0xA4 and the NT/QH302R
variants. **This is the one stable structure in the family** — the protocol-number space is
fragmented, this block is not.

| Off | W | Field | Encoding | Units | Source |
|---|---|---|---|---|---|
| 0 | 1 | year | **plain binary**, year = 2000 + Y | — | v1.8.1 §5.2.1.1 |
| 1 | 1 | month | plain binary, 1–12 | — | " |
| 2 | 1 | day | plain binary, 1–31 | — | " |
| 3 | 1 | hour | plain binary, 0–23 | — | " |
| 4 | 1 | minute | plain binary, 0–59 | — | " |
| 5 | 1 | second | plain binary, 0–59 | — | " |
| 6 | 1 | GPS-info / satellites | **high nibble = length of the GPS information (usually 0xC = 12), low nibble = satellites in use** | count | v1.8.1 §5.2.1.5 |
| 7 | 4 | latitude | **uint32 BE**, magnitude only; sign from bit 10 of the flags word | ÷ 1 800 000 → degrees (= ÷60÷30000) | v1.8.1 §5.2.1.6; LL301 §6 |
| 11 | 4 | longitude | **uint32 BE**, magnitude only; sign from bit 11 | ÷ 1 800 000 → degrees | " |
| 15 | 1 | speed | uint8 | km/h | v1.8.1 §5.2.1.8 |
| 16 | 2 | course / status | uint16 **BE** — see 3.2 | — | v1.8.1 §5.2.1.9 |

**Time base is per protocol number, not per device.** `0x12`/`0x16` carry **device-local** time in
the login-declared zone; `0x22`, `0x26`, `0x27`, `0xA0`, `0xA4`, `0x8A` are explicitly marked
`(UTC)` in LL301. Never apply one session offset to all of them. See §7 Trap 4.

**Coordinate scaling is confirmed three ways.** (1) GT07 §5.2.3 gives the ranges 0–162 000 000 for
0–90° latitude and 0–324 000 000 for 0–180° longitude — both exactly 1 800 000 per degree.
(2) The vendor worked example 22°32.7658′ → 40 582 974 → `0x026B3F3E` is consistent with minutes ×
30000 (the PDF misprints the multiplier as "X3000" in the formula while its arithmetic uses 30000).
(3) My decode of the Lithuania frame gives 54.945347 / 24.017622 against Traccar's asserted
54.94535 / 24.01762, and the co-located LBS block reports MCC 246 = Lithuania.

### 3.2 The course/status word — VERIFIED, and the asymmetry that causes real bugs

`uint16 BE`. **The bytes on the wire are `[high, low]`; read them big-endian like everything else.**

| Bit | Meaning | Polarity |
|---|---|---|
| 0–9 | course | 0–360 degrees |
| 10 | latitude hemisphere | **1 = North (positive), 0 = South (negate)** |
| 11 | longitude hemisphere | **1 = West (negate), 0 = East (positive)** |
| 12 | GPS positioned | **1 = fix valid**, 0 = not positioned |
| 13 | differential / real-time | 1 = differential positioning |
| 14–15 | documented as constant 0 by every rank-1 PDF; Traccar reads b14 as "ignition field present" and b15 as the ignition state | **INFERRED at best — see §7 Trap 12** |

**The asymmetry:** for latitude the *set* bit means positive; for longitude the *set* bit means
negative. Any implementation that treats them symmetrically mirrors half the world.

```
lat = raw_lat / 1_800_000;  if (!bit10) lat = -lat
lon = raw_lon / 1_800_000;  if ( bit11) lon = -lon
valid = bit12
```

**Fix validity is carried ONLY by bit 12.** Not by the satellite count, not by 0/0. A frame can
report 13–15 satellites and coordinates in the correct city and still be an invalid, re-uploaded,
stale fix. See §7 Trap 15 — this is the single most important behaviour in the whole document.

Recommended expression (this **diverges from CLAUDE.md hard rule 6 and therefore needs an ADR before
any code lands**):

```
fix_valid := bit12 AND NOT isNullIsland(lat, lon)
satellites is a QUALITY metric, never a validity gate for this protocol
```

Rationale: hard rule 6 defines invalid as `satellites == 0 || isNullIsland(...)`. On GT06 both of
those are true of frames the device itself marks valid, and false of frames the device marks invalid.
Ported unchanged, the house invariant misses the one bit that matters.

### 3.3 The LBS block

| Field | Width | Rule | Source |
|---|---|---|---|
| MCC | 2 (uint16 BE) | **If bit 15 is set, the MNC occupies 2 bytes and the true MCC is `mcc & 0x7FFF`** | VERIFIED — LL301 repeats the note six times (§6, §7, §9, §11, §13, §15) |
| MNC | 1 **or 2** | per the MCC bit-15 flag | " |
| LAC | **2** on 2G types, **4** on 4G types (0xA0, 0xA1, 0xA2, 0xA4, 0xA5) | VERIFIED — traccar commit `6e5481ebb`; LL301 §18 field table | |
| Cell ID | **3** on 2G, **8** on 4G | VERIFIED — same sources | |

Vendor verbatim (LL301 §18 and five other places): *"As the MNC of some countries occupies 2 bytes,
we use the MSB in MCC to differentiate the length of MNC. When the MSB in MCC is '1', the length of
the MNC is '2'. For shipped devices, Bit15 is '0' by default; while for newly-shipped devices,
Bit15 is '1'."*

**Read that last sentence again: the wire format of one SKU changed mid-production run.** Proven on
a live frame: corpus `78782322…81360104cb8a00bef3…` → MCC `0x8136` ⇒ bit15 set ⇒ MCC 310 (USA),
MNC `0x0104` = 260 (T-Mobile US), then LAC 52106, CID 48883, then ACC/mode/re-upload = 00 00 00,
consuming exactly the 12 remaining payload bytes.

**Therefore: the LBS block width is a computed function, never a constant.** Any table that writes
"LBS(8)" is wrong for newly-manufactured hardware, and the one-byte shift lands on the ACC/ignition
byte — which drives trip segmentation, idle time and, on this platform, billing.

#### 3.3.1 The LBS-length byte — the empirical rule, not the documented one

Status-bearing packets (0x16, 0x26, 0x27, 0xA4) prepend a length byte before the LBS block. The
documented rule is "self-inclusive: `1 + 2 + |MNC| + |LAC| + |CID|`" (so 9 for 2G, 16 or 17 for 4G).

**I measured every such frame in the corpus. The byte takes the values 0, 1, 8, 9, 10, 16 and 17:**

| Declared | Frames | Consistent with self-inclusive? |
|---|---|---|
| 0x00 | 1 (`78784a16…`) | no |
| 0x01 | 1 (`78782416…`) | no |
| 0x08 | **5** (four 0x16, one 0x26) | **no — 8 is structurally impossible: MCC 2 + MNC 1 + LAC 2 + CID 3 is already 8 bytes of cell data** |
| 0x09 | 10 | yes (2G) |
| 0x0A | 1 | (2-byte MNC 2G) |
| 0x10 | 2 (0xA4, 4G) | yes |
| 0x11 | 1 (0xA4, 4G, 2-byte MNC) | yes |

All of them CRC-PASS. **The firmware does not use the byte consistently — that is the finding.**

**Implement Traccar's empirical rule, which is neither convention:**

```
consume MCC/MNC/LAC/CID by the TYPE-DRIVEN widths of §3.3
then skip max(0, declared_lbs_len - 9) bytes
NEVER use the byte as an absolute seek
alarm when declared_lbs_len < 9 (firmware quirk worth a metric)
```

Implementing the "self-inclusive" rule literally seeks one byte early on **24 %** of the
status-bearing frames in the only corpus that exists. I demonstrated the damage on the CRC-valid
frame `787825161a011c141001cf00bc62e0043533a231113808028005006800124b470603300204baa49a0d0a`
(CRC 0xA49A ✓): the correct walk reads terminal-info `0x47` (ignition on, charging on, alarm code 0,
fix valid, voltage 6, GSM 3); the one-byte-early walk reads `0x4B` — alarm code 1, which every
decoder maps to VIBRATION — plus charging off, "voltage" 0x47 = 71 against a documented 0–6 range,
and GSM 6 against a documented 0–4 range. On `78782516160908063736c0006e70110442fc80…` (CRC 0x73FB ✓)
ignition flips 1 → 0, silently ending a trip. On `78782526160913063918c0…` (CRC 0x398E ✓) the
fix-valid bit flips 0 → 1, promoting an invalid position to trusted.

Nothing throws. No CRC fails. A panic alarm is fabricated out of a Cell-ID byte.

### 3.4 The 5-byte status tail — three candidate layouts, not two

Documented (v1.8.1 §5.3.1.14–18): `terminal-info(1) | voltage(1) | GSM(1) | alarm(1) | language(1)`.

**There is a third layout the vendor docs never list, and it is the one that fits some real data.**
Corpus frame `78780a130604ea04000006bc8a0d0a` (CRC 0xBC8A ✓, payload tail `06 04 EA 04 00`):

| Reading | Result | Plausible? |
|---|---|---|
| (1,1,1,1,1) | terminfo 0x06, voltage 4, **GSM 0xEA = 234** (documented range 0–4) | no |
| (1,2,1,1) | terminfo 0x06, **voltage 0x04EA = 12.58 V**, GSM 4 = strong, alarm 0x00 | **yes — a textbook vehicle supply** |
| (1,2,2) | terminfo 0x06, voltage 12.58 V, alarm 0x0400 | ambiguous |

Traccar refuses to decode this frame at all — commit `95fdfd770` changed its assertion from
`KEY_POWER 0.0` to `KEY_POWER null` after a variant collision, i.e. the reference implementation
concluded it could not tell either. **Emit the raw 5 bytes plus a model-gated interpretation; never
write a bare volts number from an un-modelled device.** §9 Q10.

**Terminal-information byte — the meaning is per protocol number, not global.** VERIFIED conflict:

| Bit | 0x13 / 0x16 / 0x19 / 0x27 / 0xA4 / 0xA5 (v1.8.1 §5.3.1.14) | 0x23 / 0x36 (LL301 §4/§5) |
|---|---|---|
| 7 | oil/electricity **disconnected** (immobiliser engaged) | cut off fuel/power |
| 6 | *"GPS tracking is on"* (v1.8.1) / *"position fixed"* (LL301) — **do not use this as a fix source; bit 12 of the flags word is the unambiguous one** | position fixed |
| 5–3 | **3-bit alarm code**: 000 normal · 001 vibration/shock · 010 power cut · 011 low battery · 100 SOS | bits 5–4 = "extended", **bit 3 = remote lock** |
| 2 | charging | charging |
| 1 | **ACC high (ignition)** | ACC on |
| 0 | activated / armed | defence on |

Traccar additionally invents alarm-nibble values **6 → GEOFENCE** and **7 → REMOVING**
(7 → OVERSPEED under the VXT01 variant) that appear in no vendor document I read. INFERRED at best.

**Priority rule, VERIFIED (LL301 §12):** when the separate alarm byte is non-zero it wins; only when
the alarm byte is `0x00` should you fall back to terminal-info bits 3–5.

### 3.6 Command channel (server → device) and correlation

```
78 78 | LEN | 80 | cmdLen(1) | serverFlag(4) | ASCII command (M) | [language(2)] | serial(2) | crc(2) | 0D0A
cmdLen = 4 + M
```

VERIFIED on LL301 §19's own example `78 78 0E 80 08 00000000 736F7323 0001 6D6A 0D0A`
(`sos#`, CRC 0x6D6A ✓).

**The Language field is optional despite being tabulated as mandatory** — VERIFIED: LL301's own
example and v1.8.1 Appendix B's `DYD,000000#` and `HFYD` commands all omit it, and all CRC-verify.

**The reply is not correlated by serial.** The device answers with a fresh serial from its own
counter and echoes the **4-byte Server Flag Bit** verbatim — that is the correlation key. VERIFIED:
v1.8.1 Appendix B pairs `78 78 15 80 0F 0001A958 "DYD,000000#" 00A0 DCF1` with
`78 78 18 15 10 0001A958 "DYD=Success!" 0002 0018 9177` — flags match, serials do not; both
CRC-verify.

Two reply shapes: legacy **0x15** (short frame, `cmdLen + serverFlag + ASCII + lang`) and modern
**0x21** (`7979` long frame, `serverFlag + encoding + text`).

**Traccar writes serverFlag `0x00000000` on every command, so it cannot correlate concurrent
commands.** Use a monotonic 32-bit token and key your command-outcome table on it.

### 3.7 Variant discrimination — the actual hard problem

**VERIFIED (rank 2).** There is no variant field on the wire. Traccar resolves the dialect with a
22-row `(header, type, LEN)` magic-number table, re-evaluated **per packet**, at the top of every
decode (`decodeVariant`, ~line 1642):

| Type | LEN → variant |
|---|---|
| 0x12 | 0x21 → BENWAY · 0x24 → VXT01 · 0x29 → WETRUST · 0x2B → S5 · ≥0x71 → GT06E_CARD |
| 0x16 | 0x24 → VXT01 · 0x26 → SEEWORLD · 0x2D → TRX16I |
| 0x24 | 0x2E → SR411_MINI · 0x31 → WANWAY_S20 |
| 0x31/0x32/0x34 | 0x2A / 0x27 / 0x29 / 0x37 → SL4X |
| 0x13 | 0x13 → OBD6 |
| 0x19 | ≥0x17 → SPACE10X |
| 0x22 | 0x2F → SEEWORLD |
| 0xA2 | 0x40 → LW4G |
| 0xA3 | 0x0C, 0x18 → SEEWORLD |
| 0x36 | 0x35 → TRX16I |
| 0x17 | 0x28 → RFID (else WiFi) |
| 0x95 | payload[0..1] == `FFFF` → **JC400** (the only rule that does not use LEN) |
| — | everything else → STANDARD |

**Three reasons this is fragile, and one reason it is still necessary:**

1. **LEN is not a namespace.** `(0x7878, 0x13, 0x0A)` is the most common frame in the family and was
   once claimed by the VXT01 rule — every plain GT06 heartbeat reported `KEY_POWER = 0.0` until
   commit `95fdfd770` removed it. A false "power lost" on healthy vehicles.
2. **LEN moves under you.** A 2-byte MNC adds one byte, so the same logical frame appears at two
   lengths, and the second length may belong to a different vendor's rule.
3. **LEN itself is untrustworthy** (§2.4).

Eight further sub-variants are **not discriminable from the wire at all** and require an
operator-supplied model string: `NT11/NT20/NT26/NT40/NT46/VL100/XT40`, `VL103/LL303/VL512/G18`,
`SEEWORLD`, `LW*`, `R11`, `QH302R`. On the NT family a 0x22 frame gains a `srcType 1 + IMEI 8 +
deviceTime 6` prefix before the GPS block — invisible except by length.

**Implementation rule:** build the table **as data**, add a CI test asserting no two rules match the
same `(header, type, LEN)` triple, treat a match as a *hint*, and gate every non-STANDARD field map
behind an explicit per-device model in the registry. A model-ambiguous frame must route to the
undecodable-records path, not to a guess.

### 4.2 `0x01` login and its ACK — the whole handshake

```
device → 78781101 0752533678900242 7000 3201 0005 1279 0D0A     (LL301 §2)
server → 78780501 0005 9FF8 0D0A                                 (LL301 §2b)
```
LEN 0x11 = 17 ⇒ total 22 ✓. IMEI BCD `0752533678900242` → drop the leading `0` nibble →
**752533678900242**. Type identifier `0x7000`. Timezone word `0x3201` → `0x320` = 800 → **UTC+8:00**,
language 1 = Chinese. Serial 0x0005. CRC 0x1279 ✓.

The ACK echoes type 0x01 and serial 0x0005; CRC over `05 01 00 05` = **0x9FF8** ✓ — byte-identical to
the vendor's printed reply. This is the entire handshake: no IMEI, no status. **If it is not sent the
device re-sends the login and never uploads a position.**

Western-hemisphere login (the only one in the corpus that exercises the sign bit):
`787811010864717003664467100f190a0002c6d20d0a` → IMEI 864717003664467, typeId 0x100F,
tz word `0x190A` → `0x190` = 400 with bit 3 set → **UTC−4:00**, language 2 = English. CRC 0xC6D2 ✓.

### 4.5 `0xA0` — a 13-satellite fix in the right city that is **invalid**

```
787829a01707150f2d0ecd01635100041e96d000087c02d4020000912e000000000718798d000e0006ed3ce50d0a
```
Source: Traccar corpus (added in commit `6e5481ebb`). CRC recomputed **0x3CE5** ✓.

2023-07-21 15:45:14 · **13 satellites** · flags **0x087C** → course 124, b10=0 **South**, b11=1

### 4.6 `0x23` modern heartbeat — 2-byte centivolts, different bit map

```
78780B23 C0 0122 04 0001 0008 1872 0D0A
```
Source: JM-LL301 §4 (also Traccar's only 0x23 frame, lifted verbatim). CRC **0x1872** ✓,
LEN 0x0B = 6 payload + 5.

`C0` terminal info under the **LL301** map: b7 = 1 **cut off fuel/power**, b6 = 1 position fixed,
b5–4 extended = 0, b3 remote lock = 0, b2 charging = 0, b1 ACC off, b0 defence off.
`01 22` voltage = 290 → **2.90 V** (the doc's own worked example: `0x019F` = 415 → 4.15 V).
`04` GSM = strong. `00 01` language/extended-port = Chinese. Serial 8.

**Traccar reads only bits 0, 1 and 2 here** — it drops b6 (fix) and **b7 (immobiliser engaged)**,
even though it reads b7 as `KEY_BLOCKED` for 0x13/0x16. On a GK310/JM device the immobiliser state is
therefore visible on a status packet and invisible on a heartbeat.

### 4.9 The TK200 length lie, decoded

```
78 78 08 13 46 06 02 00 02 04 C6 FF DE 0D 0A     ← 15 bytes; LEN 0x08 implies 13
```
CRC field `FFDE`; computed over `bytes[2..10]` (the 15-byte reading) = **0xFFDE** ✓. The frame is
*self-consistently* mis-declared: the firmware under-counted the length **and** computed the CRC over
its own wrong length byte, so the transmitted frame validates at its true 15-byte extent.

Status payload: terminfo `46`, voltage 6, GSM 2, extension `00 02`, **serial `04C6`**. Traccar 3.3
read the serial at the length-derived offset and replied `0002` — the device then delivered 5 minutes
of data and went silent for 15, forever. Take the serial from `bytes[n-6..n-5]` and this frame is
trivial.

797900BB 97 00B5 00000001 "ADDRESS" "&&" <UTF-16BE> "&&" "8613421632699" 00…00 "##" 0016 8EA5 0D0A
```
Source: JM-LL301 §15c. LEN `0x00BB` = 187 ⇒ total 193 ✓. Inner content length `0x00B5` = 181

### 4.11 `0x94` sub-type 0x0B — the same sub-type means two different things

```
79790007 94 0B 01 0A0B 5ACE 0D0A          → networkTechnology = "4G"   (content length 1)
79790008 94 0B 02E3 0486 1420 0D0A        → external power = 7.39 V     (content length 2)
```
Both CRC-verified (0x5ACE, 0x1420). There is **no length field inside 0x94** — content length is
`declared frame length − 6`. Sub-type 0x0B means "network technology" when it carries one byte and
"external voltage ÷100" when it carries two. **One byte of framing drift turns 7.39 volts into
"2G".**

## 5. Parameter / IO dictionary

### 5.0 Read this before you look for an AVL-ID table

**There is no GT06 parameter dictionary.** Unlike Teltonika — numbered AVL IDs, one published table
per model — GT06 has **no ID space, no machine-readable list, and no vendor registry**. Telemetry
beyond position arrives through **four structurally unrelated carriers**, and a decoder must
implement all four separately:

| Carrier | Where it lives | Self-describing? | Vendor doc | Traccar | flespi |
|---|---|---|---|---|---|
| **A** — status bit-field | 1 byte inside 0x13/0x16/0x19/0x23/0x26/0x27/0x36/0xA3–0xA5 | no, fixed bits | yes (two conflicting versions) | yes | yes |
| **B** — TLV extension modules | tail of 0x36, 0x37, 0x39, 0x70, 0xF1/0xF2 | **yes** (id + len + value) | partial | partial | partial |
| **C** — 0x94 information sub-types | `7979` long frames | sub-type byte, **no length** | ~25 listed | 8 implemented | ~24 params |
| **D** — vehicle data | 0x8E, 0x8C, 0x65/0x66, 0xFE | mixed | 0x8E only | 0x8C only | 0x8E/0xFE only |

**No implementation covers more than half, and the two biggest disagree about which half.**
VERIFIED: `grep -c 0x8E Gt06ProtocolDecoder.java` → 0 (Traccar implements 0x8C, not 0x8E); flespi's
protocol-number set contains 0x8E and 0xFE, not 0x8C.

### 5.1 Carrier A — the status byte

See §3.4 for the two conflicting bit maps and the decision rule (per protocol number). Companion
scalars in the same tail:

| Field | Width | Encoding | Label |
|---|---|---|---|
| Voltage level | **1** on 0x13/0x16/0x19/0x36 | ordinal enum 0–6: 0 no power · 1 extremely low · 2 very low · 3 low · 4 medium · 5 high · 6 very high | VERIFIED — v1.8.1 §5.4.1.5 |
| Voltage | **2** on 0x23 | **centivolts**: `0x019F` = 415 → 4.15 V | VERIFIED — LL301 §4 |
| Voltage | 1 on AM01 ankle bracelet | **percentage**: `0x5A` → 90 % | VERIFIED — LL301 §17 |
| Voltage | 1 on EV02 heartbeats | observed `0xF0`/`0xF1`/`0xF2` — outside every documented range | **UNKNOWN** — traccar#5361 |
| GSM signal | 1 | enum `0x00` none · `0x01` extremely weak · `0x02` weak · `0x03` good · `0x04` strong | VERIFIED both docs |
| Alarm | 1 | see §5.5 | VERIFIED |
| Language | 1 | `0x00` = *"no reply from the platform is required"* · `0x01` Chinese · `0x02` English | VERIFIED — LL301 §12 |

**The voltage byte is undecodable from the wire alone.** Four encodings share one offset, and a
device honestly reporting level 5 is indistinguishable from 5 %. LL301 §4 says the
voltage↔level mapping is *"in the Attachment"* — **the document's only attachment is the CRC table.
The mapping is not published.** Traccar guesses by magnitude
(`≤6 → level*100/6; ≤100 → percent; else silently dropped`), which is why devices reporting 0xF0
show an empty battery column for an entire model family, with no error.

**Rule: key the interpretation off `(protocol number, device model)` in a dictionary file with a
`source_url` per entry, exactly as `packages/codec` does for Teltonika AVL IDs. Assert in CI that
every model in the catalogue has an explicit battery encoding. An unmapped model emits the raw byte
and an `unknown-encoding` marker — never a number.**

GSM caveat: flespi publishes **two** parameters, `gsm.signal.dbm` and `gsm.signal.level`
(percentage), implying at least two encodings share this byte, and real frames contain `0x64` (100).
Traccar files it as `KEY_RSSI`, which downstream code will read as dBm. **Store the enum as an enum.**

### 5.2 Carrier B — TLV extension modules (the only self-describing IO channel)

Two incompatible framings of the same idea. **The length-field width depends on the protocol number:**

```
0x36 / 0x37 / 0x39 :  id uint16BE | len uint8  | value[len]
0x70               :  id uint16BE | len uint16BE | value[len]
0xF1 / 0xF2        :  tag uint16BE | len uint8 | value[len]

VERIFIED for 0x70 (six frames) and 0x37 (one frame). **0x36 and 0x39 rest on Traccar's code alone**
— and Traccar never validates inbound CRC, so its assumption has never been checked against a device
either. INFERRED.

→ tag `0x0005`, len 2, value `0x0195` = 405 → **4.05 V**. CRC 0x21AF ✓.

### 5.3 Carrier C — 0x94 information sub-types

`7979 | len(2) | 94 | subType(1) | data | serial(2) | crc(2) | 0D0A`.
**There is no inner length field:** `payload length = declared frame length − 6`. Traccar exploits
exactly this to disambiguate sub-type 0x0B.

| Sub | Payload | Scaling / units | Label |
|---|---|---|---|
| `0x00` | uint16 (+ optional 1-byte sensor id) | **÷100 V** external power (sample `94 00 00ED` → 2.37 V). Traccar files it as `adc1`, not power | VERIFIED layout, mapping INFERRED |
| `0x01`–`0x03` | custom / vendor-defined | — | UNKNOWN |
| `0x04` | ASCII `KEY=VAL;…` configuration dump | `ALM1`–`ALM4`, `STA1`, `DYD` are **hex bitmasks**; `FENCE=` carries the centre as **decimal degrees in text** | VERIFIED |
| `0x05` | [date 6] + flags 1 | bit0 door · bit1 trigger level · bit2 I/O port · bit10 input2 | VERIFIED (`…16090908081c 03` → 2022-09-09 08:08:28, door open) |
| `0x06`, `0x08` | vendor-listed, no sample | — | UNKNOWN |
| `0x09` | GPS/BDS satellite-strength block, variable | — | UNKNOWN (vendor only) |
| `0x0A` | IMEI 8 BCD + IMSI 8 BCD + ICCID 10 BCD | strip the **trailing** `f` nibble | VERIFIED (→ ICCID 8966051912408052452) |
| `0x0B` | **1 byte** = network tech (0 = 2G, >0 = 4G) · **2 bytes** = **÷100 V** external power | **disambiguated ONLY by frame length** | VERIFIED, **undocumented in every vendor PDF** |
| `0x0C` / `0x0D` | ASCII ThinkSonic fuel string `!AIOIL,…` | see §5.4 | VERIFIED (index and body disagree; **body wins: 0x0D**) |
| `0x0E` | `(type 1, addr 1, value 2, unit 1) × n`; unit 1 = height, 2 = percent, 3 = volts | — | vendor only, nobody implements |
| `0x10`, `0x11` | vendor-listed, no sample | — | UNKNOWN |
| `0x15`–`0x17` | vendor-listed, no sample | — | UNKNOWN |
| `0x1B` | RFID / driver ID: ASCII `RFID:…` **or** binary `02 08 <4B id> <cks> 03` | canonical representation **UNDECIDED** — Traccar returns hex on some variants and decimal on others | VERIFIED (`4277efef`) |

| `0x1D` | epoch 4 + n 1 + uint16[n] | **÷100 V per second** | vendor only |
| `0x1E` | int32 temperature + int32 humidity | **÷10 both** — `000000d5 000002ee` → **21.3 °C / 75.0 %** | VERIFIED |
| `0x1F` | uint16 BE temperature | **NO DIVISOR PUBLISHED, no sample** — §9 Q5 | **UNKNOWN** |

| `0x22`, `0x24`–`0x30` | vendor-listed, no sample | — | UNKNOWN |

> **Notation warning.** The upstream research bundle's scaling column mixed "×10" and "/10" for the
> same field: it wrote `0x1E` as "**×10** both" while its own verified sample (213 → 21.3 °C) is a
> **divide**. A literal implementation reports 2130 °C. That particular error is loud. The danger is
> the fields where the direction *cannot* be checked against a sample — `0x1F` and module `0x007F`'s
> humidity. **Expose those as raw integers with an explicit `unscaled` marker; never a bare
> degrees/percent value.**

Traccar implements **8** of the ~25 vendor-listed sub-types: `00, 04, 05, 0A, 0B, 0D, 1B, 1E`.

### 5.4 The `!AIOIL` fuel-sensor string — expose both candidates

LL301 §20 documents **nine** fields and names field 2 *"Output value of the fuel level sensor (unit:
cm)"*. Real frames and Traccar's regex have **ten**. Traccar ignores field 2 and reports field 6
(*"measured value"*) as fuel.

```
!AIOIL,02,008.290,029.600,519J,0400,008.430,0,00,AB
        ^field2 = 8.290              ^field6 = 8.430
```

Both are plausible fuel numbers. **Trust the real frame for the field count; trust neither for which
field is "the" fuel. Expose both, named separately** (`fuel_sensor_output_cm`, `fuel_measured`), and
let the installer calibrate.

### 5.5 The alarm enumeration

**The only complete alarm dictionary in existence is JM-LL301 §23**: trackers `0x00`–`0x7E`, plus
`0xFE` ACC-ON / `0xFF` ACC-OFF; DVRs `0x80`–`0xA1`; ET110N `0xC0`–`0xC5`; other `0xD0`–`0xD3`.
`0x6A`–`0x6F` are unassigned.

Core codes (VERIFIED, LL301 §12 "Alarm and Language Details"):

| Code | Meaning | Code | Meaning |
|---|---|---|---|
| `0x00` | normal (fall back to terminal-info bits 3–5) | `0x11` | powered off |
| `0x01` | **SOS** | `0x13` | tamper / cover |
| `0x02` | power cut | `0x15` | powered off, low battery |
| `0x03` | vibration | `0x16` | sound-control alarm |
| `0x04` | entered fence | `0x17` | rogue base station |
| `0x05` | left fence | `0x18` | cover removed |
| `0x06` | overspeed | `0x19` | **low internal battery** |
| `0x09` | **tow / theft** (LL301) vs **vibration** (GT06F) — see below | `0x3E` | key press |
| `0x0A` | entered GPS blind spot | `0x4C` | harsh cornering |
| `0x0B` | left GPS blind spot | `0xFE` | ACC ON |
| `0x0C` | **powered on** | `0xFF` | ACC OFF |
| `0x0D` | GPS first fix | `0x0E` | **low external power** (LL301) vs **low battery** (GT06F) |
| `0x10` | SIM changed | `0x30` | **harsh braking** |

**Four codes where the reference implementation contradicts two vendor documents.** These are the
ones that fabricate customer-visible false alarms:

| Code | Vendor docs | Traccar | Consequence of Traccar's mapping |
|---|---|---|---|
| `0x0C` | LL301 §23 *and* GT06F: **power-on** | `ALARM_TAMPERING` | **a tamper alert on every boot** — a fleet that power-cycles at ignition generates one per trip, and operators switch alarms off entirely |
| `0x30` | LL301 §23 *"harsh braking"*; v1.9.0 §5.3.1.17 *"sudden brake"* | `ALARM_JAMMING` unless the model is VL* | a **GPS-jamming alert for every hard brake** |
| `0x09` | LL301 *"tow/theft"*; GT06F *"vibration"* | `TOW` on VL models, `GEOFENCE` on TRX16I, else `VIBRATION` | false theft alerts at every speed bump on half a mixed fleet |
| `0x0E` | LL301 *"low external power"*; GT06F *"low battery"* | `LOW_POWER` on TRX16I, else `LOW_BATTERY` | opposite ends of the vehicle |

**Codes Traccar does not handle at all** (they fall through to null): `0x0A`, `0x0B`, `0x0D`, `0x10`,
`0x15`, `0x16`, `0x17`, `0x3E`, `0xFE`, `0xFF`. So ACC ON/OFF reported through the alarm byte,
SIM-swap, and **rogue base station** (an anti-jamming signal worth money) are all silently dropped.

**Rule: the alarm map is a per-model dictionary entry with a `source_url`, never a `switch`.** A code
with no model-scoped entry must yield `unknown alarm, code preserved`, never a guess.

## 6. Vehicle data (CAN / FMS / OBD)

Four carriers, none complete, and the two biggest implementations support **disjoint** subsets.

### 6.1 `0x8E` — the only vendor-documented CAN packet, and nobody has ever seen one

Source: JC100 §5.5.1 (rank 1). **Label: spec-only. UNVALIDATED.** No hex sample exists in any corpus
I searched, and Traccar has zero occurrences of the byte.

```
date 6 | OBD blocks (N bytes) | sats 1 | lat 4 | lon 4 | speed 1 | course/status 2
N = packetLength - 23
each block: type 1 | dataLen 1 | data[8] | checksum 1        (11 bytes)
checksum = "negated after all data is summed" — SCOPE UNSTATED (§9 Q7)
```

| Block type | Data byte | Field | Units / scaling |
|---|---|---|---|
| `0x21` | Data0 | door / brake / engine / turn-light bits | bitfield |
| | Data1 | small light, door lock, trunk, hood, handbrake, anti-theft (2 bits), ignition | bitfield |
| | Data2 | average fuel consumption | **÷10 L/100 km** |
| | Data3 | average speed | km/h |
| | Data4–5 | **engine RPM, little-endian, unscaled** | rpm |
| | Data6 | window / remind bits — the doc lists "Bit5" twice and omits bit 4 (the left-front entry is almost certainly bit 4) | bitfield |
| | Data7 | seat belt, wiper, harsh brake/accel, 4× tyre pressure | bitfield |
| `0x22` | Data0–2 | **mileage, 24-bit little-endian** | **KM** |
| | Data3 | battery | **÷10 V** |
| | Data4 | breakdown | 0/1 |
| | Data5 | hw version nibble + car-model bits | — |
| | Data6–7 | remaining fuel | **÷10 L** |
| `0x23` | | temperature | **(LE16 − 1000) ÷ 10 °C** |
| | | PM2.5 | LE16, µg/m³ |
| | | renew mileage | `Data5*256 + Data4` — **the labels say Data4 is the high byte and the formula says Data5 is; the formula is executable, so use it (little-endian)** |
| | | steering-wheel angle | **encoding CONTRADICTORY — see §9 Q8b** |

flespi's 0x8E mapping corroborates types 0x21 and 0x22 field-for-field
(`can.trunk.status`, `can.average.speed`, `can.fuel.consumption.distance` L/100 km,
`can.fuel.volume` litres).

**Three hazards if you implement this speculatively:**
1. The block carries a `dataLen` field but the layout hardcodes `data[8]`. If `dataLen` is ever
   anything but 8, the walk desynchronises.
2. The per-block checksum's scope is unknown, so you cannot self-check a block boundary.
3. `N` derives from the declared packet length — the exact field real firmware gets wrong by 2.

**Cheap integrity check the vendor never mentions: blocks are 11 bytes, so `N mod 11 == 0` must
hold, and the post-block walk must land exactly on the serial number. If either fails, emit nothing.**

### 6.2 `0x8C` — the OBD packet that actually exists in captures (undocumented)

```
7979 | len(2) | 8C | date 6 | ignition 1 | ASCII "KKS=HEXVAL,KKS=HEXVAL,…" | 12 undocumented bytes | serial 2 | crc 2 | 0D0A
```
Both corpus frames pass CRC (I verified 0xC594 and 0x0091), so they are genuine device output.
Keys are 2 hex digits (the PID) plus **a trailing character that is always `3`** — meaning
**UNKNOWN** (§9 Q11). Values are variable-width hex, 1–8 digits, **except `4A` which is raw ASCII VIN
and may be empty**.

Decoded, both frames, uniform **÷100**:

| Key | Frame 1 | Frame 2 | Reading | Units | Label |
|---|---|---|---|---|---|
| `0x28` | 1609.84 | 0.00 | device total mileage | km | INFERRED |
| `0x2B` | 0.00 | 0.00 | fuel level | **% (not litres)** | INFERRED — two of three sources say percent |
| `0x2D` | 72.00 | 63.00 | **coolant temperature** | °C | VERIFIED by internal consistency |
| `0x30` | 14.30 | 14.50 | **battery** | V | VERIFIED |
| `0x35` | 85.00 | 58.00 | **vehicle speed** | km/h | VERIFIED |
| `0x36` | 2450.00 | 1666.00 | **engine RPM** | rpm | VERIFIED |
| `0x39` | 8.75 | 5.22 | fuel consumption rate | L/h | INFERRED |
| `0x46` | 6.61 | 0.86 | trip mileage | km | INFERRED |
| `0x47` | 254.03 | 0.15 | fuel used (Traccar) vs relative throttle % (flespi) | **contested** | INFERRED — 254 % is impossible for a throttle, 0.17 % is impossible for a moving car, so the samples refute flespi's label |
| `0x48` | 1.03 | 0.17 | absolute throttle (flespi) | **contested** | UNKNOWN |
| `0x49` | 37.84 | 0.00 | engine hours | **hours** | INFERRED |
| `0x4A` | *(empty)* | `KNAF241CMK5014255` | **VIN** | 17 ASCII (Kia) | VERIFIED |
| `0x17`, `0x22`, `0x3A`, `0x50` | 0 / 1 / 10.29 / 0 | 0 / 1 / 9.01 / 0 | — | — | **UNKNOWN** |

Frame 2 is a coherent driving snapshot — 1666 rpm, 58 km/h, 63 °C coolant, 14.5 V, 5.22 L/h — which
is what confirms the ÷100 rule for the whole packet: **internal consistency, not documentation.**

**The 12 bytes between the ASCII payload and the serial are undecoded by every implementation.**
Verbatim samples: `cb03850c3603c025af5414a6`, `c0041df0940f89c067000000`, `cb03851f5f03c020525514a7`.
They do not parse as lat/lon (÷1 800 000 gives >1000 degrees) nor as an MCC-first LBS block. Frames 1
and 3 share the prefix `cb0385` and carry consecutive serials, so the field is slowly varying per
device. **UNKNOWN** (§9 Q12).

### 6.3 `0x65` (DTC) and `0x66` (PID) — declared, never decoded

Traccar declares both constants and implements neither; its own test asserts `verifyNull` for the
0x66 frame. Real 0x66 payload:
`date 6 | ignition 1 | ",2110=0003d284,2105=00001c20,210b=00002e7c,…"` — a **different, four-hex-digit
key space** (`0x21xx`) from 0x8C's two-digit space, with the same 12-byte trailer. **UNKNOWN mapping.**

### 6.4 Raw CAN, and where the real numeric CAN set actually lives

flespi exposes `can.data.frame` (hex string, *"indexed by CAN message ID or element identifier"*) on
**protocol 0xFE** — raw CAN passthrough, no vendor doc.

**Critically:** of flespi's 381 Concox parameters, the numeric CAN/OBD set — RPM, coolant, engine
load, MAF, MAP, torque, DTC array, VIN, fuel consumed, throttle — is reachable **only through the
jt808 flavour** (`Message ID 0x0010`, and transparent message type `0xF0` of `0x0900`), **not**
through GT06 binary frames. J1939 arrives there as PGN-indexed values:

| PGN | Name | Field | Units |
|---|---|---|---|
| `0xF004` | EEC1 | engine speed | rpm |
| `0xFEE0` | VD | total vehicle distance | km |
| `0xFEEC` | VI | vehicle identification | VIN string |
| `0xFEF1` | CCVS | wheel-based speed | km/h |
| `0xFEFC` | DD | fuel level | % |

flespi's parameter split: 129 GT06-flavour-only, 124 jt808-flavour-only, 82 both.

**Practical conclusion: if a customer needs real CAN/FMS data, a GT06-flavour Concox device is the
wrong purchase.** The GT06 binary channel gives you 0x8C's dozen PIDs (undocumented, ÷100, one
vendor) or 0x8E (documented, unvalidated, zero samples). Anything richer means jt808 — a different
protocol with a 14-digit ident — or a Teltonika with a CAN adapter.

### 6.5 Scalings that will ship as plausible wrong numbers

This is the "looks right on the dashboard, is off by 1000×" list.

1. **Odometer, everywhere.** Traccar writes `KEY_ODOMETER` (documented **metres**) from: 0x8C key 0x28
   which is ÷100 of a **km** value (**1000× low**); module 0x002E read BE-as-LE; SL4X ×10; WETRUST
   raw; NT-model 24-bit. LL301 0x22 defines a 4-byte *"mileage statistics"* **with no unit at all**;
   v1.9.0 §5.2.1.14 says only *"do mileage calculation and showed by hex"*. The only behavioural
   evidence is four field frames from Mexico where the value goes 521 → 532 over ~8 minutes with the
   vehicle **stationary** — consistent with metres, absurd as 0.1 km, and the reporter claims it is a
   **temperature sensor**. **UNKNOWN** (§9 Q13).
2. **Engine hours.** `KEY_HOURS` is milliseconds in Traccar's model; 0x8C key 0x49 is written as
   `raw/100` → 37.84 **milliseconds** instead of ~37.84 hours (**3.6 million× low**).
3. **Fuel.** 0x8C key 0x2B is written to `KEY_FUEL` (litres) but is a **percentage**. Traccar's own
   original commit `e21c10d3` used `KEY_FUEL_LEVEL` (percent) and was later changed — a regression.
4. **`0x94` sub-type 0x1F** — "temperature, 2 bytes big-endian", no divisor, sitting next to a ÷10
   neighbour.
5. **`0x8E` type 0x23 steering angle** — the doc says *"high bit = direction, low 7 bits = integer
   part, second byte = fractional part"*, then gives `0x20 0x50` → 20.5°, which only works if the
   bytes are **BCD**. A binary reading gives 32.80°. It also says *"biggest angle is 40 degree"*,
   contradicting a 7-bit field.
6. **flespi ID `0x0127`** is mapped to **both** `can.engine.motorhours` (hours) and
   `can.engine.run.time` (seconds). One wire field cannot be both.
7. **Signed / overflow reads.** A 3-byte odometer read signed goes negative past 8 388 607; engine
   hours `readMedium() * 60 * 1000` overflows a 32-bit int. Traccar shipped both
   (fixed in commit `c743f3edf`, 2026-03-24).
8. **`0x8C` values ≥ `0x80000000`** overflow `Integer.parseInt(v, 16)` and **throw, discarding the
   whole position**.

**Rule: no unit-bearing field is written to a typed column unless its scaling has a `source_url` or a
verified sample. Everything else goes to a raw/named-unit attribute.**

### 6.6 Vendor arithmetic typos that will mislead a careful reader

VERIFIED, all four found while cross-checking:

* GT06F: *"049F converted to decimal is 101183"* — it is **1183**.
* JM-LL301 §20: *"401 indicates 40.2 Celsius"* for a ÷10 field — it indicates **40.1** (the adjacent
  humidity example, 855 → 85.5 %, is correct).
* JM-LL301 §2: *"12.45*100 = 1246"* while the hex it gives, `0x4DD`, is **1245**.
* v1.8.1 §5.2.2's worked example prints the satellite byte as `0xCC` while the field table above it
  and Appendix B print `0xCF`. **The example's own CRC 0x8081 verifies only with `0xCF`** (with
  `0xCC` I compute 0x7377), proving `0xCC` is a typo — which Traccar imported verbatim into its test
  corpus, where it fails CRC.
* GT06F's 0x12-with-mileage example is a broken copy-paste of v1.8.1's: 40 bytes on the wire with
  LEN `0x1F` and v1.8.1's CRC for the 36-byte no-mileage frame. The correct values are LEN `0x23`,
  CRC `0x6190` — which v1.9.0 §5.2.1 finally prints correctly (I verified 0x6190).
* GT07's login example CRC `0x7193` does not verify under any range I tried (I compute 0xCF81), and
  Traccar imported it verbatim.

## 7. THE TRAP LIST

Every entry is a decoding bug that has already been shipped by somebody — mostly by Traccar, which is
the most careful implementation in existence. Each carries **symptom → cause → source → the test that
catches it**. Nothing here is hypothetical.

The common shape: **it never throws, it never fails a CRC, every value stays in a storable range.**

---

### Trap 1 — Latitude hemisphere bit polarity is inverted from the naive reading
**Label: VERIFIED (rank 2, shipped for a year).**
**Symptom.** Every position mirrored across the equator. A São Paulo fleet (−23.5) plots at +23.5 in
the Atlantic north of Brazil. Distance and geofences are computed on the mirrored point, so trips are
nonsense but internally consistent — nothing errors.
**Cause.** The vendor table labels bit 10 *"South Latitude, North Latitude"* with no explicit 0/1
mapping (v1.8.1 §5.2.1.9, BYTE_1 Bit2). Reading it left-to-right as 0 = South gives the wrong answer.
**The rule is: bit 10 SET means NORTH; negate the latitude when it is CLEAR.**
**Source.** Traccar commit `ccefc3b34` "Fix GT06 decoder hemisphere issue" (2015-10-22), a one-line
flip: <https://github.com/traccar/traccar/commit/ccefc3b34>
**Test.** A fixture *pair*, one per hemisphere, asserting the sign:
`787819100e010903230ec803ae32a60653cded00180000020072feb70d0a` (b10=0 → **−34.304377**, Buenos Aires)
against the §4.1 Lithuania frame (b10=1 → **+54.945347**). A polarity flip must fail **both**.
⚠ Do **not** use `78781f1210020e140613cc…` as the southern vector — I decoded it and it is
**+41.616293 / +2.266337, Spain, northern hemisphere**. It would not catch the bug.

### Trap 2 — Reading the course/status word little-endian
**Label: VERIFIED (I found this in the source material for this very document).**
**Symptom.** Every position mirrored, every course scrambled, every fix marked invalid — and the
decoder is entirely self-consistent, so nothing looks wrong until a customer complains.
**Cause.** On the reference 0x12 frame the two bytes are `54 00`. The upstream research bundle
printed the field as "`0054`" — the little-endian read — while stating bit conclusions that only
hold for `0x5400`. An implementer reconciling the discrepancy concludes the field is little-endian,
contradicting the envelope's "all multi-byte fields big-endian".
**Source.** The frame itself, `78781f120f0a140e150bc505e51e780293a9e800540000f601006e0055da00035f240d0a`
(Traccar corpus, Apache-2.0), against Traccar's assertion `position(…, true, 54.94535, 24.01762)` —
`valid = true` with a positive latitude reconciles only with `0x5400` BE (b10 = 1, b12 = 1).
**Test.** Assert the raw flags word equals `0x5400` for that frame, not just the decoded outputs. A
value assertion on lat/lon alone will pass a decoder that has two compensating bugs.

### Trap 3 — Timezone read as a scaled integer instead of packed decimal HHMM
**Label: VERIFIED (rank 2, shipped for a year).**
**Symptom.** Every timestamp lands hours or days away; reports for "today" come back empty because
every fix is filed under a different date. Half-hour zones (India +5:30, Iran +3:30, Nepal +5:45,
Chatham +12:45) are wrong by 18–27 minutes even after the gross error is fixed.
**Cause.** `offset = (extensionBits >> 4) * 36000`. The field looks like a scaled integer and is a
packed decimal. Correct: `hours = v/100; minutes = v%100; negate if (bits & 0x08)`.
**Source.** Traccar commit `8f0c648c6` "Fix GT06 timezone decoding" (2015-04-23):
<https://github.com/traccar/traccar/commit/8f0c648c6>
**Test.** Decode a login whose extension word is `0x2120` and assert **+5:30 = 19 800 s**; decode
`0x3208` and assert **−8:00**. A `*36000` implementation yields +53 h and −80 h. **Assert the offset
in seconds, not merely that a date parses.**

### Trap 4 — The time base is per protocol number, not per session
**Label: VERIFIED (rank 1 + rank 5).**
**Symptom.** A device declaring GMT+8 that sends UTC in 0x22 lands 8 hours off, while its 0x12 frames
are correct — on the same connection.
**Cause.** `0x12`/`0x16` carry device-local time in the login-declared zone; `0x22`, `0x26`, `0x27`,
`0xA0`, `0xA4`, `0x8A` are individually marked `(UTC)` in LL301. GT06F contradicts *itself* — its
protocol-number table says `0x12 Positioning Data (UTC)` and its own packet table nine pages later
says `0x12 (device time zone and time)`.
**Source.** <https://github.com/traccar/traccar/issues/1676>; LL301 §6 vs GT06F.
**Test.** Two fixtures with identical GPS blocks under types 0x12 and 0x22 for a device declaring
+8:00, asserting UTC results 8 hours apart. Then a runtime alarm: when a *real-time* fix's device
time differs from receive time by exactly the declared offset, raise a provisioning warning.

### Trap 5 — Two firmware generations of the same model need opposite timezone treatment
**Label: VERIFIED (rank 5, field report).**
**Symptom.** Half the fleet is 8 hours out. A server-wide offset fixes them and breaks the other half.
Customers see two vehicles at the same depot with timestamps 16 hours apart.
**Cause.** Firmware built 2013/12/28 emits device-local time in 0x12; firmware built 2015/04/27 emits
UTC. **The protocol number does not change — the wire is indistinguishable.**
**Source.** <https://github.com/traccar/traccar/issues/1676> (three trackers built 2013/12/28 needed
`gt06.timezone=28800`; 2015/04/27 units were correct without it). The build date **is on the wire**:
`[VERSION]GT06D_20_60DM2_B25E_V15_WM[BUILD]2013/12/28 15:24` in a `7979`/0xFD frame (Traccar returns
`verifyNull` for it — it is discarded), and `[BUILD]2014/04/07 10:59` in traccar#873.
**Test.** Parse and persist the 0xFD/0x21 version string per device. Then a regression test: the same
0x12 payload from two devices whose stored build dates straddle the cutover must yield different UTC
results. **Timezone must be a per-device resolved value, never a protocol-wide config key.**

### Trap 6 — The device's declared timezone can simply be a lie
**Label: VERIFIED (rank 5, first-hand).**
**Symptom.** `fixTime` is 5 h 30 m behind `deviceTime` and `serverTime` on every record. The map is
right, the history is wrong, "last position" looks stale by hours, so the vehicle appears offline in
reports while showing live on the map.
**Cause.** The login timezone byte reflects a configuration register the firmware does not apply to
the timestamp path. It is declared intent, not observed fact.
**Source.** <https://www.traccar.org/forums/topic/fix-time-gt06-concox/> — a Chinese EV02 declared
+00:00 and reported in +05:30; fixed by SMS `GMT,E,0,0#`.
**Test.** Not a unit test — a **commissioning check**. On first login, compare the device's first
position timestamp against server receipt time; if the delta is within 60 s of a whole or half hour
while the login declared 0, raise a provisioning warning. **Store the declared offset AND the observed
skew as separate device attributes.**

### Trap 7 — The ACK does not echo the device's serial
**Label: VERIFIED (rank 5 with logs, rank 2 shipped 2014–2018).**
**Symptom.** The device re-sends the same record until it sees its own serial back. History fills with
exact duplicates and, on metered SIMs, the data bill multiplies. It "works sometimes" because the two
counters occasionally coincide.
**Cause.** `response.writeShort(++serverIndex)` — a per-decoder counter instead of the frame's serial.
**Source.** <https://github.com/traccar/traccar/issues/3704> (request 0053 → response 0003, 0054 →
0004, 0055 → 0005; *"Device keeps sending same data package until it receives confirmation with their
Serial number"*), fixed by commit `e2e050187` reading `buf.getShort(buf.writerIndex() - 6)`.
**Counter-evidence, kept honest:** LL301 §4b's own heartbeat ACK example carries serial 0x0100 against
request 0x0008 and CRC-verifies, and `vondraussen/gt06` hard-codes 0x0001 in production. Echo
enforcement varies by firmware. **Echo it anyway.**
**Test.** Round-trip over the whole filtered corpus: the emitted ACK's serial bytes must equal
`input[-6:-4]` and the emitted CRC must verify. Plus a simulator scenario that withholds a matching
serial and asserts the simulated device retransmits — proving the harness can see the failure at all.

### Trap 8 — The declared length is wrong by 2 on real firmware, and the serial moves with it
**Label: VERIFIED (rank 5, with hex).**
**Symptom.** The device transmits normally for ~5 minutes, goes silent for ~15, forever. On the
server it flips online/offline on a fixed cycle and loses three quarters of its positions. **Nothing
is logged: the frames parse, they are just answered wrongly.**
**Cause.** `78780813460602000204c6ffde0d0a` declares LEN 0x08 (implying 13 bytes) and is 15 bytes.
Reading the serial at `2+1+8-4` gives `0x0002`; the true serial is `0x04C6`. The CRC was computed by
the firmware over its own wrong length byte, so the frame **passes CRC at its true extent**.
**Source.** <https://github.com/traccar/traccar/issues/1727>; Traccar's workaround commit `dac5c6923`
literally special-cased `type == MSG_STATUS && length == 13 → length += 2`, later replaced by trailer
validation in `cff01fd43`.
**Test.** Feed `787808134606020002044dc5050d0a` and assert (a) the framer returns a **15-byte** frame,
(b) the ACK echoes **0x0204**, not the byte pair at the declared offset. **Rule: locate the serial
relative to the END of the frame, never relative to the declared length.**

### Trap 9 — "Reject LEN < 5" silently deletes the entire WiFi/LBS sub-family
**Label: VERIFIED (measured on the corpus).**
**Symptom.** Underground-parking and urban-canyon positions vanish. No error, no metric — the
customer's stolen-vehicle case has a hole exactly where the tracker was indoors.
**Cause.** 11 of 12 unique 0x17/0x69 frames declare LEN `0x00`, `0x03` or `0x08` on real frames of
26–107 bytes, because the length slot is the **AP count**. A numbered framer that applies the length
sanity rule before reading the type byte discards them all.
**Source.** My measurement of `Gt06ProtocolDecoderTest.java`; the shape is documented nowhere but
Traccar's `MSG_WIFI` branch (`wifiCount = buf.getUnsignedByte(2)`).
**Test.** Feed the four corpus 0x17/0x69 frames back to back in **one** TCP segment and assert exactly
four frames with correct boundaries and zero structural slack. Then assert `787801080d0a` (the genuine
runt) is still rejected. Both must hold — that is what proves the ordering is right.

### Trap 10 — Reading the length field as SIGNED
**Label: VERIFIED (rank 2, shipped until 2014-08-28).**
**Symptom.** Any frame declaring ≥128 bytes (multi-cell LBS, `7979` information frames, photo chunks,
JC400 media lists) computes a negative total. The framer never assembles it, the device never gets an
ACK, and it retransmits forever while the customer sees **no data at all from that message class**.
**Cause.** Java's `byte` is signed; `0x80..0xFF` read as −128..−1.
**Source.** Traccar commit `e7d203230` "Fix GT06 frame decoder" (`getByte` → `getUnsignedByte`,
`getShort` → `getUnsignedShort`): <https://github.com/traccar/traccar/commit/e7d203230>
**Test.** Frame a real long frame — e.g. the 154-byte `787895a2…` (LEN 0x95 = 149) — and assert the
framer returns 154 bytes. **In TypeScript the equivalent trap is `readInt8`/`readInt16BE`; ban the
signed readers in the codec lint rules.**

### Trap 11 — Framing by scanning for `0D 0A`
**Label: VERIFIED (three real frames).**
**Symptom.** RFID card swipes, temperature readings and transparent serial data arrive truncated; the
CRC then fails and the trailing serial+CRC are read as the start of the next frame, desynchronising
the stream. The customer sees a driver-ID reader that "works for a while then stops".
**Cause.** ASCII/transparent payload types terminate their own text with CRLF **inside** the frame.
**Source.** Corpus, all three CRC-PASS with the interior CRLF inside the CRC span:
`79790019941b524649443a3030384642324245424133390d0a000c14930d0a` (0x94/0x1B, `RFID:008FB2BEBA39\r\n`),
`797900109b0344373532304136320d0a000f87f00d0a` (0x9B, `D7520A62\r\n`),
`7979000e9b0332382e33a1e60d0a0289be490d0a` (0x9B, `28.3` + GB2312 `℃` + CRLF).
**Test.** Assert each is returned whole (31, 22 and 20 bytes) and that the decoded payload still ends
with CRLF, and that each CRC verifies after framing. **A truncating framer fails CRC — that is the
cheap detector.**

### Trap 12 — Framing by scanning for the `78 78` start pattern
**Label: VERIFIED (rank 4 — the most-used Node implementation does exactly this).**
**Symptom.** Any payload byte pair equal to `78 78` (ASCII `xx`, very common in transparent text, and
reachable in binary coordinate and cell fields) splits one frame into two garbage frames. Separately,
a frame arriving in two TCP reads throws "unknown message header" and is dropped — under packet loss
or MTU pressure the device silently loses records.
**Cause.** `sliceMsgsInBuff()` uses `Buffer.indexOf('7878')` and `parse()` throws unless the chunk
begins with `0x7878`. **There is no accumulation buffer.**
**Source.** <https://github.com/vondraussen/gt06/blob/master/gt06.js>; its issue #19 is titled
*"Why are you clearing the buffer instead of waiting for more data?"*
**Test.** Property test: concatenate three corpus frames and feed the concatenation to the framer at
**every possible split point** and byte-at-a-time; assert the same three frames every time. Include
one synthetic frame whose payload contains `78 78` and one containing `0D 0A`.

### Trap 13 — One malformed frame permanently kills the session
**Label: VERIFIED (rank 5).**
**Symptom.** Device shows offline. Support asks the customer to power-cycle the tracker, which fixes
it (new TCP connection), so the fault is blamed on the hardware. Position history has a hole that
ends exactly at a reconnect.
**Cause.** Once the framer mis-slices, every subsequent boundary is wrong, and a CRLF fallback can
lock onto the wrong CRLF and stay wrong.
**Source.** <https://www.traccar.org/forums/topic/gt06-protocol-issue/> — *"sending in between few
strings which are not starting by 7878 or 7979. After that server has stopped responding to the
genuine pings also"*; Tananaev: *"If the length is incorrect, there's no way for server to properly
separate messages in the stream."*
**Test.** Inject 7 bytes of random garbage between two valid frames; assert the framer discards only
the garbage and decodes the following frame, **and** that `ingest_frame_resync_total` increments.
Silent recovery is nearly as bad as no recovery — you lose the signal that a firmware is misbehaving.

### Trap 14 — Variant discrimination on `(header, type, length)` collides between vendors
**Label: VERIFIED (rank 2, with a shipped regression).**
**Symptom.** Every plain GT06 heartbeat reported `KEY_POWER = 0.0 V` — a false "power lost" on healthy
vehicles — because an ordinary `(0x7878, 0x13, 0x0A)` status frame was classified as VXT01 and its

**Source.** Traccar commit `95fdfd770` "Fix GT06 protocol conflict" (2023-08-03) removes the rule and

<https://github.com/traccar/traccar/commit/95fdfd770>
**Test.** Build the variant table **as data** and assert in CI that **no two rules match the same

### Trap 15 — Correct decoding requires an operator-typed model string
**Label: VERIFIED (rank 2).**
**Symptom.** Two identical trackers in one fleet: the one whose "model" field says `NT20` decodes
correctly; the one where the installer left the field blank reads the **embedded IMEI bytes as
latitude and longitude** and plots the vehicle at an impossible place with a date years off. No
error — both look like valid positions.
**Cause.** `hasStatus(0x22, model)` is true only for `{NT11, NT20, NT26, NT40, NT46, VL100, XT40}`;
`hasLength` derives from it; and
`if (type == MSG_GPS_LBS_2 && modelNT) { readUnsignedByte(); skipBytes(8) /* imei */; setDeviceTime(); }`
runs **before** the GPS block. Alarm codes `0x09/0x0E/0x28/0x29/0x30` also branch on model.
**Source.** `Gt06ProtocolDecoder.java` (`NT_MODELS`, `hasStatus`, `hasLength`, `decodeAlarm`); that
the coupling breaks in practice: commit `248a3927d` "Ignore model name case" — devices decoded wrongly
because someone typed `nt20`; commits `807492c48`, `f06ecf340` show the list growing model by model.
**Test.** Decode one NT20 0x22 frame twice — with and without the model set — and assert the unset
case **FAILS LOUDLY** (routes to the undecodable-records path) rather than producing a position. Also
assert model matching is case- and whitespace-insensitive.

### Trap 16 — Fix validity is carried ONLY by bit 12 ★ the most important trap in this document
**Label: VERIFIED (rank 2 cross-checked against rank 1).**
**Symptom.** A parked vehicle accumulates a slow drift of "positions" that are individually plausible
— right city, right street even — but are stale repeats. They inflate trip distance, flap geofence
enter/exit, and turn idle time into driving.
**Cause.** The device re-uploads its last known fix on a timer while stationary, marking it invalid
via **bit 12** while leaving satellites and coordinates populated. **Neither `satellites == 0` nor the
0/0 null-island rule catches it.**
**Source.** `787829a01707150f2d0ecd01635100041e96d000087c02d4020000912e000000000718798d000e0006ed3ce50d0a`
(Traccar corpus, commit `6e5481ebb`; CRC 0x3CE5 re-verified by me) → 2023-07-21 15:45:14,
**13 satellites**, −12.936676 / −38.396418 (Salvador, Brazil; LBS MCC 724 = Brazil corroborates),
speed 0, flags `0x087C` → **b12 = 0**, and its trailing bytes are ACC `00`, **upload mode `0x0E`**,
re-upload `00`. LL301 defines `0x0E` as *"GPSDUP upload (upload at a fixed interval in still state)"*.
Bit-12 semantics: v1.8.1 §5.2.1.9, BYTE_1 Bit4 *"GPS having been positioning or not"*.
**Test.** A fixture asserting that frame yields `fix_valid = false` **despite satellites = 13 and
non-zero coordinates**, plus a pipeline test asserting such a record contributes **zero metres** to
trip distance and does not change geofence state. ⚠ **This contradicts CLAUDE.md hard rule 6 as
written and requires an ADR before code lands** — rule 6's `satellites == 0 || isNullIsland` is true
of frames the device marks valid and false of frames it marks invalid.

### Trap 17 — An unhandled protocol number becomes a position at (0, 0) in 1970
**Label: VERIFIED (rank 5 + my own decode).**
**Symptom.** The customer's map shows the vehicle at Null Island dated 1969/1970. Because it looks
like a position it enters trip distance and drags every trail across the Atlantic to (0,0).
**Cause.** A default-constructed position object is returned for an unknown type. Protocol `0x42`
(a 4G variant) is in no type table, yet its first 18 payload bytes are the **identical** GPS block
used by 0x12/0x22/0xA0 — the protocol-number space is fragmented, the GPS block is not.
**Source.** <https://www.traccar.org/forums/topic/gt06-data-not-translated-correctly/> —
`7878254216041d121b28cf046ad05809218450001c00013604b9ff00685b0d0000685b0d001a000b0d0a`. I decoded it:
LEN 0x25 matches its 42 bytes, CRC field `0x000B` = my computed `0x000B`, 2022-04-29 18:27:40,
15 sats, 41.171676 / −85.106391 (Indiana), flags `0x1C00` (valid, N, W), MCC `0x0136` = 310 = USA —
self-consistent on four axes.
**Test.** Two tests. (1) Unknown-type frames must **never** yield a position: assert the 0x42 frame
produces an undecodable-record retaining the raw bytes. (2) A *generic* GPS-block recovery path gated
on `LEN ≥ 0x25 and the 18-byte block parses to a sane date, |lat| ≤ 90, |lon| ≤ 180, satellites ≤ 24`
should recover it — assert it yields 41.171676 / −85.106391.

### Trap 18 — MNC width is selected by the MOST SIGNIFICANT BIT of MCC, and it changed mid-production
**Label: VERIFIED (rank 1, note repeated six times).**
**Symptom.** Cell-tower geolocation for a **subset of one model** resolves to the wrong country or
fails; worse, every field after the LBS block shifts by one byte, so **ignition, battery and odometer
are silently wrong for exactly those units**.
**Cause.** MCC is at most 999, so bit 15 is free and was repurposed as a width flag. A parser reading
MCC as a plain uint16 gets 33532 instead of 724 and then reads the wrong number of MNC bytes.
**Source.** JM-LL301, verbatim: *"As the MNC of some countries occupies 2 bytes, we use the MSB in MCC
to differentiate the length of MNC. When the MSB in MCC is '1', the length of the MNC is '2'. For
shipped devices, Bit15 is '0' by default; while for newly-shipped devices, Bit15 is '1'."*
**This means the wire format of one SKU changed mid-production run — the units a 2026 deployment
actually receives are the ones with bit 15 set.**
**Test.** Decode two frames from the same model, one with bit 15 set and one clear, asserting the same
MCC value and **different MNC widths**, and asserting the byte AFTER the LBS block (ignition) is right
in both. Assert MCC is always masked to 15 bits before storage — an unmasked 33532 in the cell-lookup
query is the visible symptom. Real 2-byte-MNC frame:
`78782EA4110C0C02281BF6026C18720C38D22800149C1181CC00010000260E000000000615F8012C05041102FF001058FD0D0A`
(CRC 0x58FD ✓, MCC `0x81CC` → 460, MNC `0x0001`).

### Trap 19 — LAC is 2 bytes on most types and 4 on the 4G types
**Label: VERIFIED (rank 2 with a shipped regression).**
**Symptom.** Ignition reported ON for a parked vehicle (or vice versa), because the ACC byte is read
from the middle of the cell ID. Trips start and end at random, mileage reports are fiction, and driver
scores are computed on phantom trips.
**Cause.** No single vendor doc covers all types; the widths were discovered one message type at a
time. 4G types (0xA0, 0xA1, 0xA2, 0xA4, 0xA5) use LAC 4 / CID 8.
**Source.** Traccar commit `6e5481ebb` "Fix VL03 ignition decoding" (2023-07-24) — the entire fix is
adding `|| type == MSG_GPS_LBS_7` to the `lac = buf.readInt()` branch, and the test it adds asserts
`KEY_IGNITION false` on the Salvador frame: <https://github.com/traccar/traccar/commit/6e5481ebb>.
Vendor confirmation: LL301 §A0's example decodes only with a 4-byte LAC (`0x00002866`), giving
MCC 460 and 22.577780 N / 113.930062 E = Shenzhen (the vendor's home city).
**Test.** A per-type LBS layout table with one fixture per type, each asserting the **first byte after
the LBS block** (usually ACC/ignition). Testing the cell ID alone will not catch a width error that
happens to produce a plausible number; testing the byte *after* it will.

### Trap 20 — Treating the LBS-length byte as an absolute seek
**Label: VERIFIED (I measured it — see §3.3.1).**
**Symptom.** A spurious VIBRATION alarm fabricated from a Cell-ID byte; ignition flipping 1 → 0 and
silently ending a trip; an invalid fix promoted to valid. All on CRC-valid frames.
**Cause.** The documented "self-inclusive" rule (`1+2+|MNC|+|LAC|+|CID|`) is not what the firmware
emits. Measured values across the corpus: `{0:1, 1:1, 8:5, 9:10, 10:1, 16:2, 17:1}`. **8 is
structurally impossible under self-inclusive**, yet 5 CRC-valid frames declare it.
**Source.** My measurement; Traccar's empirical rule is

**Test.** Decode `787825161a011c141001cf00bc62e0043533a231113808028005006800124b470603300204baa49a0d0a`

error**, not a datum — assert the decoder raises it.

### Trap 21 — Reading a 6-byte iButton/driver ID as an 8-byte long
**Label: VERIFIED (rank 2, fixed 2026-02-27).**
**Symptom.** The wrong driver is attributed to every trip on that vehicle; payroll and driver-behaviour
reports are wrong for a whole fleet. The ID looks like a plausible number, so nobody suspects it until
a driver disputes a trip.
**Cause.** `String.valueOf(buf.readLong())` over a 6-byte field — which also **over-reads the buffer by
2 bytes**. Correct: `(readUnsignedInt() << 16) | readUnsignedShort()`.
**Source.** Traccar commit `71a73dee6` "Fix iButton decoding": the expectation for
`78782e610869412070143950190a1e0d3806c802b0eb0f0561ecdc00d80002d404000004215f0e000001395581000d1ca60d0a`
changes from `1345759281165` to **`20534657`**: <https://github.com/traccar/traccar/commit/71a73dee6>
**Test.** Assert the exact string `20534657`, **and** assert the read cursor sits exactly at the
serial-number offset afterwards — a cursor-position assertion catches over-reads that a value
assertion misses. Also **decide and document ONE canonical representation** (hex vs decimal): Traccar
has both, so the same physical card yields two different IDs on two device models.

### Trap 22 — Signed reads and 32-bit arithmetic on cumulative counters
**Label: VERIFIED (rank 2, fixed 2026-03-24).**
**Symptom.** Odometer goes negative past 8 388 607; the customer's mileage report shows −8 000 km and
delta-based billing blows up. Engine hours overflow and wrap.
**Cause.** `readMedium()` is signed in Netty; `readMedium() * 60 * 1000` overflows `int` before being
widened to `long`.
**Source.** Traccar commit `c743f3edf` "GT06 NT20 protocol correction, hours should be long and
odometer should be read as unsigned": <https://github.com/traccar/traccar/commit/c743f3edf>
**Test.** Synthesise a 0x22 NT20 frame with odometer `0xFFFFFF` and hours `0xFFFFFF`; assert
**16 777 215** and **1 006 632 900 000** — not −1, not a wrapped negative. Property test: odometer
must be monotonically non-decreasing within a device session; any decrease is surfaced as an anomaly,
not stored.

### Trap 23 — Guessing the battery encoding from the value's magnitude
**Label: VERIFIED (rank 1 vs rank 2 conflict).**
**Symptom.** A device genuinely reporting **level 5 of 6** is displayed as **5 %**, so the customer
gets a "battery critical" alert on a healthy tracker. Devices whose byte reads `0xF0`/`0xF1`/`0xF2`
show **no battery at all** — an empty column with no error, for an entire model family.
**Cause.** `if (battery <= 6) level = battery*100/6; else if (battery <= 100) level = battery; /* else
nothing */`. Four encodings share the offset (§5.1) and two of them overlap in 0..6.
**Source.** v1.8.1 §5.4.1.5 (ordinal 0–6) vs LL301 §4 (2-byte centivolts) vs LL301 §17 (percentage,
*"0x5a refers to 90%"*) vs traccar#5361 (`0xF0`). Traccar needed model-specific branches anyway —
commits `410260640`, `807492c48` (`battery / 10.0` volts on NT models), `381e25ab3` "Improve EV02
battery level", `37ed39472` "Seeworld battery level decoding".
**Test.** **Refuse to guess.** Key the interpretation off `(protocol number, model)` in a dictionary
file and assert in CI that every catalogued model has an explicit battery encoding. Add a fixture
where the raw byte is `0x05` and assert it is **not** silently turned into 5 % for a level-encoding
model, and one with `0xF0` asserting an `unknown-encoding` marker rather than nothing.

### Trap 24 — Shipping one alarm map for the whole family
**Label: VERIFIED (rank 1 vs rank 2, four separate codes).**
**Symptom.** A TAMPER alarm on every boot, so a fleet that power-cycles at ignition generates one per
trip and operators switch alarms off entirely. Half a mixed fleet gets false tow/theft alerts at every
speed bump; the other half gets GPS-jamming alerts for every hard brake.
**Cause.** One decoder serves many brands; the alarm byte was standardised only for `0x01`–`0x06`.
See the table in §5.5 for the four contested codes.
**Source.** Traccar `decodeAlarm`: `case 0x0C, 0x13, 0x25, 0x32 -> ALARM_TAMPERING`,
`case 0x30 -> modelVL ? ALARM_BRAKING : ALARM_JAMMING`,
`case 0x09 -> variant == TRX16I ? ALARM_GEOFENCE : modelVL ? ALARM_TOW : ALARM_VIBRATION`.
Vendors: LL301 §23 (`0x0C` power-on, `0x30` harsh braking, `0x09` tow/theft), GT06F (`0x0C` power on,
`0x09` vibration), v1.9.0 §5.3.1.17 (`0x30` sudden brake). The churn is visible in the history:
`bc893da78`, `2ab6df0a5`, `b0de34f54`, `82754e889`, `a0c77b0c4`, `95151f242`, `e718b74be`.
**Test.** The alarm map is a per-model dictionary entry with a `source_url`, never a `switch`. CI test:
every alarm code present in any fixture resolves through a **model-scoped** table; a code with no

must produce POWER_ON, **not** TAMPERING.

### Trap 25 — Traccar's own test corpus contains hand-mutated vendor examples with stale CRCs
**Label: VERIFIED (I identified each one).**
**Symptom.** You seed golden fixtures from Traccar, enable CRC validation as the vendor requires, and
~1 in 7 fixtures goes red. You are then tempted to "fix" the fixture — which our hard rule 9 forbids.
**Cause.** Traccar never validates inbound CRC, so nothing there catches an edited payload. Five
provable cases:

| Frame | Edit | CRC field | True CRC |
|---|---|---|---|
| `787811010123456789012345100B3201000171930D0A` | IMEI anonymised from the GT07 vendor original | `7193` | **`CF81`** |
| `78782627…8002001900FF00004DF60D0A` (0x27) | alarm/language `0C 01` → `19 00` | `4DF6` | **`C359`** |
| `78782DA4…4605041900FF01908A640D0A` (0xA4) | alarm/language `13 02` → `19 00` | `8A64` | **`FFBA`** |
| `78783B2E10010D…0005B14B0D0A` (0x2E) | **only the type byte** changed from 0x28 | `B14B` | **`5D85`** |
| `78783c220109999999999999991a…` | IMEI anonymised to 9999999999999999 | — | fails |

**Source.** My recomputation of all 183 corpus frames; the vendor originals are in LL301 §12, §13 and
§8 and all three CRC-verify.
**Test.** Three things. (1) A CRC suite from frames whose CRC verifies, asserting the covered range is
exactly `[length byte … last serial byte]`. (2) A **counted, metered** CRC-failure path

one model instead of as missing data. (3) **A guard in `tools/redact`: after rewriting an IMEI in a

passes CRC. Our Teltonika redaction habit will otherwise manufacture this exact defect.

### Trap 26 — Not validating inbound CRC at all
**Label: VERIFIED (rank 2, measured).**
**Symptom.** Corrupted frames decode into plausible-looking positions and the customer gets a phantom
trip. There is no other symptom — that is the point.
**Cause.** `Checksum` is referenced exactly once in `Gt06ProtocolDecoder.java`, in `sendResponse()`.
`Gt06FrameDecoder.java` does not reference it at all.
**Source.** Vendor requirement, LL301 field table: *"If the receiver receives a packet that contains a
CRC error, it ignores the error and discards the packet."*
**Test.** Flip one payload bit in a known-good frame and assert the decoder emits nothing, increments
the metric, and **does not ACK**. Assert the ACK path is unreachable from a CRC-failed frame.

### Trap 27 — Emitting a bogus ACK for a runt frame
**Label: VERIFIED (rank 2).**
**Symptom.** The server answers a 6-byte frame with an ACK whose "serial" is `0x7878` — the header
bytes read from before the start of the frame.
**Cause.** `787801080d0a` exists in the corpus: LEN 0x01 leaves no room for the mandatory serial and
CRC. Traccar computes `dataLength = length - 5 = -4`, returns null from the type handler, and the
fall-through path then does `buf.getShort(writerIndex - 6)` = `getShort(0)` = `0x7878`.
**Test.** Ship it as an underflow fixture: assert the framer rejects it and that **no ACK is emitted**.
Any code doing `buf.slice(n-6, 2)` without a length guard reads before the buffer start.

### Trap 28 — Looping the multi-LBS cell list until the bytes run out
**Label: VERIFIED (rank 1 example).**
**Symptom.** Four bogus cell towers at LAC 0 / CID 0 are emitted per packet, polluting the
cell-geolocation table and dragging LBS-derived positions toward a nonexistent tower.
**Cause.** The record list in 0x18/0x28/0x2E (and 0xA1) is **fixed-count (7 records) and
ZERO-PADDED**, terminated by `0xFF`.
**Source.** LL301's own example
`78783B2810010D02020201CC00287D001F713E287D001F7231287D001E232D287D001F4018 0000000000000000000000000000000000 00FF 0002 0005 B14B 0D0A`
(CRC 0xB14B ✓) — four real neighbour records, then four all-zero records, then the `0xFF` terminator.

### Trap 29 — Field selection by `readableBytes() == N`, and the stray trailing `0x00`
**Label: INFERRED from VERIFIED observations (rank 2).**
**Symptom.** For the affected units, ignition, archive flag and odometer are **simply absent** — the
attributes never appear, with no error and no log line. In a mixed fleet this looks like "some
trackers don't support ignition", and the customer is told to buy different hardware.
**Cause.** Traccar gates these on exact remaining-byte counts:
`buf.readableBytes() == 3 + 6`, `== 3 + 4 + 6`, `== 4 + 6`, `== 18`, `== 22`, `> 75 + 6`. A single
stray byte selects a different field map. And the stray byte is real: `78781511…0034 10FFDD 00 0D0A`
(type 0x11) declares LEN 0x15 = 21 and carries `00` before the CRLF; `7878121011091c0b1b2999…` (type
0x10) declares 18 with 24 bytes actual.
**Test.** Take any 0xA0 frame that decodes ignition/upload-mode/archive correctly, **append one `0x00`
before the CRLF**, and assert the same three fields still decode. An offset-from-the-end parser
passes; a `readableBytes() == N` parser silently drops all three. Make it a property test over every
position fixture.

### Trap 30 — Discarding the upload-mode and re-upload flags
**Label: VERIFIED (rank 1 fields + rank 5 customer impact).**
**Symptom.** Buffered records a device flushes hours later are treated as live. The customer gets
overspeed and geofence alerts at 03:00 for a trip that happened at 21:00, and a vehicle "drives" its
whole backlog in the ten seconds after it reconnects.
**Cause.** Traccar reads the bytes only under exact length equalities, **discards** the upload-mode
byte in one branch (`buf.readUnsignedByte(); // upload mode`), and sets `KEY_ARCHIVE` to `false` in
one branch and `null` in another. **There is not one `KEY_ARCHIVE` assertion in its 658-line GT06
test file.**
**Source.** LL301 §A0 field table — *"GPS data re-upload | 1 | 0x00: Real-time upload; 0x01: Re-upload
(unavailable on GT06)"* and "Data upload mode" with `0x04` (last fix after moving→still), `0x05`
(*"last valid fix prior to reconnection from a network interruption"*), `0x0A`/`0x0D` (last position
after going still), `0x0E` (GPSDUP fixed-interval-while-still). Identical list in JC100 §5.3.1.15–16.
Customer impact: <https://www.traccar.org/forums/topic/potentially-incorrect-code-in-gt06-protocol-decoder-for-location-data-packet/>
**Test.** Assert on the Salvador frame that `upload_mode == 0x0E` and `re_upload == 0x00` are surfaced
as **named fields**; assert on its sibling `787829a0170704112226cf…` (CRC 0x6B8F ✓) that
`upload_mode == 0x03` (ACC change) and `ignition == true`. Then a pipeline test: a record with
`upload_mode ∈ {0x04,0x05,0x0A,0x0D,0x0E}` or `re_upload == 0x01` **must not raise real-time alerts**.
**Parse these by absolute offset from the end of the frame, never by `readableBytes()` equality.**

### Trap 31 — Turning heartbeats into position rows
**Label: VERIFIED (rank 2 + two independent field threads).**
**Symptom.** A parked vehicle generates a database row every 300 s, all at identical coordinates, all
with the same `fixTime`. Duplicate/skip filters then behave pathologically — one user found that with
GT06 *"fixTime remains same until next ignition on"*, so a fixTime-based skip limit filters out
**everything** and the device appears offline. Storage and query cost scale with the **idle** fleet.
**Cause.** `getLastLocation(position, null)` is called on **18 separate code paths** in the GT06
decoder, including `MSG_HEARTBEAT` and every LBS-only branch. The result is indistinguishable from a
real fix downstream except for `fixTime`.
**Source.** <https://www.traccar.org/forums/topic/device-j16-with-gt06-protocol/> and
<https://www.traccar.org/forums/topic/does-filterduplicate-and-filterskiplimit-works-well-for-gt06-protocol/>
(Tananaev: *"Everything will be filtered out, yes"*).
**Test.** Assert a 0x13/0x23 status frame produces a **device-state event** (battery, GSM, ignition,
presence) and **NOT** a position row. Then a pipeline test: 20 consecutive heartbeats from a stationary
device add **zero rows** to `positions` and zero metres to trip distance, while still updating
last-seen. This is our existing GPS-jitter rule applied one layer earlier.

### Trap 32 — Allocating a media buffer from a wire-declared size
**Label: VERIFIED (rank 2, hardened 2026-06-20).**
**Symptom.** Server memory grows without bound on a fleet with cameras (JC400/JC261/X1). A single
malformed photo header can request a ~2 GB allocation. Ingest OOMs or GC-thrashes and **every device
on that node loses its session at once** — which triggers a synchronised reconnect-and-flush storm.
**Cause.** `ByteBuf photo = Unpooled.buffer(buf.readInt()); photos.put(pictureId, photo);` with removal
only on the success path, in a `Map` held by the decoder.
**Source.** Traccar commit `7c00b1c83` "Harden media buffers (fix #5920)"; traccar#5920: *"Without
validation, a malformed packet can request up to 2.1GB allocations. Successfully allocated buffers
persist in the photos HashMap with no cleanup mechanism"*. Also traccar#873, an
`ArrayIndexOutOfBoundsException` crash on a `7979`/0xFD frame.
**Test.** Extend the simulator's `oversize` scenario to GT06: a photo header declaring `0x7FFFFFFF`
must be rejected **before allocation**, and an abandoned transfer must be reaped on session close.
Assert a hard cap constant **and** assert the reaper runs — a leak test that only checks the happy
path proves nothing.

### Trap 33 — `0x94` sub-type 0x0B disambiguated only by frame length
**Label: VERIFIED.**
**Symptom.** A 7.39 V external supply is reported as the string `"2G"`, or a network-technology flag
is reported as 0.01 V. Both are storable, neither errors.
**Cause.** There is no length field inside 0x94; content length is `declared length − 6`. Sub-type
0x0B carries one byte (network tech) or two (÷100 V) with no in-payload discriminator.
**Source.** `79790007940B010A0B5ACE0D0A` (CRC 0x5ACE ✓) vs `79790008940b02e3048614200d0a` (CRC 0x1420 ✓).
Sub-type 0x0B appears in **no** vendor document.
**Test.** Both frames as fixtures, asserting `networkTechnology == "4G"` and `power == 7.39`
respectively. Then assert that a 0x94 frame whose content length matches **neither** arm yields an
`unknown-subtype` record rather than a guess.

### Trap 34 — Bits 14/15 of the course word read as ignition
**Label: INFERRED at best, and disputed.**
**Symptom.** An ignition reading manufactured out of bits every rank-1 vendor document (v1.8.1,
v1.9.0, GT06F, GT07, LL301) shows as constant 0. On the reference Lithuania frame b14 = 1, so Traccar
reports `ignition = false` for it — a datum with no source.
**Cause.** Traccar reads b14 as "ignition field present" and b15 as the value; asked for the source on
the forum, Tananaev answered *"How many GT06 documents have you checked? There is a million different
variations."* In my corpus b14 = 1 on 12 frames and b15 = 1 on 7, correlating with plausibly-moving
vehicles — so the bits are **not always zero in the field**, but nothing establishes their meaning.
**Source.** <https://www.traccar.org/forums/topic/potentially-incorrect-code-in-gt06-protocol-decoder-for-location-data-packet/>
**Test.** Gate the claim on a known model. Assert that for an unmodelled device the ignition attribute
is **absent**, not `false` — and note traccar#2832, where absent attributes treated as `false` flipped
ignition off and produced false trip boundaries.

### Trap 35 — Reading only the first TLV module, and reading modules little-endian
**Label: VERIFIED (rank 2).**
**Symptom.** Odometer 673 062 912 instead of 9 000; two of three sensors silently missing from every
0x37 frame.
**Cause.** No loop on protocol 0x37 (Traccar reads one module); `readUnsignedIntLE` on module 0x002E
and on 0x0034's timestamp while every neighbouring field is big-endian.
**Source.** The CRC-valid frame `7878353714080d05000ac5…002e0400002328 003b0217c0 003c0401020001 002c468a0d0a`
(CRC 0x468A ✓) carries **three** modules; `Gt06ProtocolDecoder.java:1437`.
**Test.** Assert three modules are returned from that frame and that module `0x002E` decodes to
**9000** (big-endian). Assert the walk consumes the payload exactly — a TLV walk that ends with
leftover bytes is a parse error.

### Trap 36 — Deduplicating on the serial number
**Label: VERIFIED (rank 5).**
**Symptom.** True duplicates are stored twice (they carry different serials); true distinct records
are dropped after a device reboot (the counter restarts at 1 and collides with history).
**Cause.** v1.8.1 §4.5: *"The serial number of the first GPRS data sent after booting is '1'"* — it is
per-**boot**, wraps at 0xFFFF, and repeats. traccar#5460 contains two frames identical in every byte
including the timestamp, differing only in serial (`0x3C81`/`0x3C80`) and CRC — I verified both
CRC-PASS (0xD7AC, 0xC625).
**Test.** Both frames as fixtures; assert the pipeline stores **one** position. Dedup key:
`(device_id, device_time, lat, lon)`.

### Trap 37 — ACKing before the record is durably queued
**Label: VERIFIED (rank 2 behaviour).**
**Symptom.** Silent, permanent data loss on any ingest crash or queue failure — invisible, because the
device believes the record delivered the moment `write()` returned and the protocol gives it no way
to learn otherwise (§2.8.1).
**Cause.** Traccar emits the ACK inside the protocol decoder and returns the Position afterwards; the
old `server.instantAcknowledgement` switch no longer exists.
**Test.** Fault-injection: fail the XADD and assert **no ACK is emitted** and the connection is closed.
Then assert the p99 ACK latency stays under the 5 s deadline with the durable write in the path — this
is the test that catches "we made it correct and now it times out".

### Trap 38 — Wake-from-sleep zero fixes
**Label: VERIFIED (rank 5/6).**
**Symptom.** A vehicle jumps to Null Island for two or three records when a vibration wakes the
tracker, then returns.
**Cause.** *"Some trackers, when in sleep mode and activated by vibration, will send data several
times to the server with 0 longitude and 0 latitude or Valid No before sending valid data."*
**Test.** This one **is** caught by `isNullIsland` (ADR-039) — assert it. It is the *weak* form of the
invalid-fix problem; Trap 16 is the dangerous one.

### Trap 39 — Implausible clocks: dead RTCs and GPS week rollover
**Label: VERIFIED phenomenon, UNCERTAIN specific claim.**
**Symptom.** A GT06N from 2010 reporting 2004-09-28; device/fix times jumping by minutes, hours or
days; a cluster of devices whose timestamps are shifted by ~19.7 years.
**Cause.** Dead RTC on boot before first fix, and the 10-bit GPS week counter rolling over
(1999-08-21, 2019-04-06). flespi's Concox changelog reportedly carries an entry *"Added logic to parse
timestamps affected by 'GPS Week Number Rollover' problem"* — **I could not load the raw thread, so
treat the wording as unconfirmed**; the underlying phenomenon is independently documented
(<https://www.gps.gov/news/gps-week-number-rollover>).
**Test.** Clamp: a timestamp before the device's stored manufacture/build year, or more than a few
minutes in the future, routes to an anomaly channel rather than being stored. **Record both the
device-declared time and the server receipt time on every record** — you cannot reconstruct this later.
Fixture: the all-zero date/time LBS frame `7878151100000000000001CC00266A001DF10001001891880D0A`
(CRC 0x9188 ✓, month 0 and day 0) must **not** become a valid timestamp — this is the vector that
catches naive `new Date(year, month-1, …)` arithmetic.

### Trap 40 — Refusing to answer unprovisioned devices
**Label: VERIFIED (rank 1 warns about it explicitly).**
**Symptom.** An unprovisioned tracker reconnects in a tight loop and burns the customer's data plan;
on a public server it is a nuisance, on ours it is a bill.
**Cause.** GT07 §5 says *"Server will not reply … to device which has not been registered"* and
Traccar follows it (it only ACKs when a `DeviceSession` exists). v1.8.1 §III.7 says the opposite and
names the failure mode: *"it will lead to a continuous reconnected by the terminal and the GPRS
traffic will be consumed heavily."*
**Test.** Assert that a login from an unknown IMEI receives a valid ACK, stores nothing, is
rate-limited, and closes after a grace period. Assert the rate limiter actually fires under a flood.

### Trap 41 — Answering an alarm with the wrong protocol number
**Label: VERIFIED by CRC arithmetic (the two source documents disagree).**
**Symptom.** An SOS or panic alarm is never acknowledged, so the device retransmits, hits the 5 s
ladder, and reboots — during the emergency it was reporting.
**Cause.** LL301 §12's *table row* says the reply to 0x27 is typed **0x26**; its own printed *example*
is `78 78 05 27 00 1C C7 5A 0D 0A`. I computed both: CRC over `05 27 00 1C` = **0xC75A** (matches the
printed value); over `05 26 00 1C` = **0x9D86** (does not). **The example is internally consistent at
0x27 — the table row is a copy-paste from the 0x26 section.**
**Test.** Assert the ACK builder emits type `0x27` for a 0x27 alarm and that its CRC verifies. And
assert the language-byte rule: an alarm whose language byte is `0x00` gets **no** reply
(LL301: *"No reply from the platform is required"*).

### Trap 42 — Storing multi-LBS RSSI as dBm
**Label: VERIFIED conflict.**
**Symptom.** Serving-cell signal stored as −62 dBm when the vendor's scale says 62 is a *strength* on
a 0–255 axis. Cell-geolocation weighting is then inverted.
**Cause.** LL301 §8: *"Its value range is 0x00–0xFF, where '0x00' indicates the signal is the weakest;
while '0xFF' the strongest"*, and its own example descends 62, 49, 45, 24 from the serving cell
outward. Traccar does `int rssi = -buf.readUnsignedByte();`.
**Test.** Assert the four neighbour RSSIs from the 0x28 frame are stored as **62, 49, 45, 24** with an
explicit `scale: "vendor-0-255"` tag, and that the serving cell has the highest value. Traccar's
negation is a display convention, not a decode — do not store it as dBm.

### Trap 43 — `Integer.parseInt` on OBD hex values ≥ 0x80000000
**Label: VERIFIED (rank 2).**
**Symptom.** The **entire position is discarded** because one OBD field overflowed — a thrown exception
inside the decoder, so nothing is stored and nothing is logged as a decode failure.
**Cause.** 0x8C values are variable-width hex up to 8 digits; `Integer.parseInt(v, 16)` throws above
`0x7FFFFFFF`.
**Test.** Fixture with a `0x8C` key whose value is `FFFFFFFF`; assert the position still decodes, the
offending key is surfaced as unparsed, and nothing throws.

### Trap 44 — Trusting the packet count in `0x8E` OBD blocks
**Label: INFERRED (the packet is spec-only — no sample exists anywhere).**
**Symptom.** A fuel or RPM byte becomes a latitude, because the block walk drifts into the GPS block
that follows it.
**Cause.** `N = packetLength − 23` derives from the field real firmware gets wrong by 2 (Trap 8); the
block declares a `dataLen` that the documented layout ignores in favour of a hardcoded `data[8]`; and
the per-block checksum's scope is unstated, so there is no boundary self-check.
**Test.** Assert `N mod 11 == 0` and that the post-block walk lands **exactly** on the serial number;
if either fails, emit nothing. Until a real 0x8E capture exists, this branch must refuse to emit
rather than emit a best guess.

### 8.3 Vectors that must exist and do not

Write these as **skipped tests with a comment**, so the gap is visible in CI output rather than
invisible in someone's head:

| Missing vector | Why it matters |
|---|---|
| Any **0x2D** frame | The only location packet with delivery semantics. Zero frames of type 0x2D exist anywhere. Its layout is INFERRED from one sentence. |
| Any **0x8E** frame | The only vendor-documented CAN packet. Spec-only. |
| Any **0x65** DTC frame | Declared, never captured. |
| **0x14** (satellite info), **0x39**, **0x40** (BMS), **0x41** (multimedia), **0x82**, **0xA9**, **0xB0**, **0xB2** | Declared by Traccar, no frame anywhere. Flying blind. |
| The **0x35 → 0x36 photo transfer flow** | One 0x35 photo-info frame exists (`78781f3511061a0b24330503107d06084889cb01000100000cfa20e3acd301333fcb0d0a`, CRC 0x3FCB ✓); the chunked download — server sends pictureId + offset + size, device replies with **binary that may contain 0D 0A** — is entirely unexercised, and it is the flow most likely to break a framer. |
| **Server→device coverage generally** | Only four captured server frames exist in total (login ACK, 0x8A time reply, 0x80 command, 0x17/0x97 address replies), all from vendor PDFs. Traccar's test file contains **zero** server-bound frames. Every ACK we emit is validated only by CRC reconstruction plus those four. |
| A **login + position pair with independently known wall-clock time** | Nothing proves the "0x12 is device-local, 0x22 is UTC" rule end to end; it is inferred from two specs and Traccar's `DateBuilder(timezone)` usage. |
| A **half-hour-timezone login** | The HHMM decode is confirmed only against a vendor illustration of UTC−12:45, a zone that does not exist. |

## 9. Open questions

Nothing here is compressed. Each entry: **what is unknown → what would settle it → how much it
matters.** "Matters" is scored for *our* platform (fleet tracking, billing on ignition hours,
geofence and overspeed alerting, white-label customers).

### Framing and session

**Q1 — Serial-number wrap behaviour at 0xFFFF.** Does it wrap to 0x0000 or to 0x0001?
*Settled by:* a long-running capture from one device across ~65 k packets, or a vendor firmware note.
*Matters:* **low.** We do not use the serial as a key (Trap 36). Only affects a diagnostic.

**Q2 — The trailing `0x00` before CRLF in the serial-less 0x17/0x69 WiFi frame.** Candidate: language
byte. Candidate: reserved. Traccar never reads it.
*Settled by:* a vendor doc describing that frame — none of the six PDFs mentions it — or a capture
where the byte is non-zero.
*Matters:* **low** for decode (the structural walk lands on it either way), **medium** for framing
confidence: it is one of the bytes the walk must consume exactly.

**Q3 — Is the bespoke `7878 00 <type> <6B time> 0D0A` reply to 0x17/0x69 actually required?**
Traccar sends it; the device in traccar#5841 kept transmitting either way.
*Settled by:* a controlled A/B against a real device (send / don't send) watching reconnects.
*Matters:* **medium.** If required and omitted, WiFi-scan positions stop, which is exactly when the
customer needs them (indoors).

**Q4 — What is the 0x2D "backup action"?** Re-sent later on the same session, re-sent after
reconnect, or merely written to flash? The English is a translation artefact.
*Settled by:* the Chinese-language original of LL301 §6, or a capture with deliberate ACK suppression
on a 0x2D-capable device.
*Matters:* **high.** 0x2D is the only packet where the ACK buys durability. It is the one place where
ACK-after-persist has a defined payoff, and we cannot verify the payoff.

**Q5 — Does any firmware genuinely reject a non-echoing ACK?** Two counter-examples exist
(vondraussen hard-coding 0x0001; Traccar 3.3 sending 0002 for serial 04C6 with no *immediate*
reconnect), and one strong positive (traccar#3704).
*Settled by:* a bench test replying with a deliberately wrong serial and watching the reconnect timer.
*Matters:* **low** — we echo it regardless. Useful only for understanding a customer's symptom.

**Q6 — Does any GT06-family device ever speak UDP?** Every doc is silent; Traccar is TCP-only; one
rank-6 blog calls the device's UDP setting a firmware bug.
*Settled by:* a vendor configuration manual for the `SERVER` command listing a working UDP mode.
*Matters:* **low** now, **medium** later — a UDP path would change the whole ingest shape.

**Q7 — The exact ACK deadline enforced by shipping firmware.** Docs say 5 s (v1.8.1, JC100, LL301) or
10 s (GT07); one rank-6 page claims 30–60 s.
*Settled by:* instrumented delay injection against a real device.
*Matters:* **high.** It is the p99 budget for our entire ingest path including the durable write. If
the real number is 5 s we have less headroom than a Teltonika deployment.

**Q8 — Is the login timezone field really packed decimal HHMM?** Both *real* captures are whole-hour
zones (+8:00, −4:00), which the wrong reading also decodes correctly. The only discriminating example
is a vendor illustration of UTC−12:45 — a zone that does not exist on Earth.
*Settled by:* one capture from a +5:30 / +5:45 device pairing its login extension word with a
position whose true wall-clock time is independently known.
*Matters:* **high for those regions, zero elsewhere.** An 18-minute error is small enough to pass
review and large enough to lose a "was the vehicle at the depot at 09:00" dispute.
*Mitigation until settled:* store the raw device-time bytes **and** the raw extension word; resolve
the offset at render, never bake it at ingest; expose a per-device override.

**Q8b — Is the "0x12 is device-local, 0x22 is UTC" rule true end to end?** It is inferred from two
specs plus Traccar's `DateBuilder(timezone)` usage. GT06F contradicts itself within one PDF.
*Settled by:* a capture pairing a login extension with a position whose real time is known.
*Matters:* **high.** Everything downstream — trips, reports, billing by hours — sits on it.

### Field widths and layout

**Q9 — What protocol number does the server use to acknowledge 0x19 / 0xA5 LBS alarms?** LL301 §17b
says 0x26; there is no CRC-checkable example in either direction. (For 0x27/0xA4 the question is
*settled*: the CRC arithmetic proves 0x27.)
*Settled by:* a vendor example carrying a printed CRC, or a bench test replying with each type and
watching for retransmission.
*Matters:* **high.** These are SOS and panic packets; an unacknowledged alarm retransmits, then the
5 s ladder, then a device reboot — during the emergency it was reporting.

**Q10 — The 5-byte status tail is three-way ambiguous**, not two-way: `(1,1,1,1,1)`, `(1,2,1,1)` and
`(1,2,2)` all fit. On `78780a130604ea04000006bc8a0d0a` (CRC-valid) reading A gives GSM 234 (documented
range 0–4) and reading B gives a textbook 12.58 V supply.
*Settled by:* two consecutive frames from one device whose real supply voltage **and** signal bars are
known independently.
*Matters:* **high.** Voltage drives low-battery and power-cut alerting, which is a paid feature.

**Q11 — Is the LBS-length byte ever meaningful as an absolute length?** Measured values across the
corpus: 0, 1, 8, 9, 10, 16, 17 — and 8 is structurally impossible under the documented convention.
*Settled by:* nothing available today. **The finding is that the firmware does not use it
consistently.** A 4G capture declaring 15 or 16 from a device known to use an exclusive count, or the
per-model PDF for whichever firmware emits 8 on a 2G frame, would settle the *convention*.
*Matters:* **critical.** See §10 — this is the riskiest byte in the protocol.

**Q12 — What are the 12 bytes between the ASCII payload and the serial in every 0x8C and 0x66 frame?**
Undecoded by every implementation. Samples: `cb03850c3603c025af5414a6`, `c0041df0940f89c067000000`,
`cb03851f5f03c020525514a7`. Not lat/lon (÷1 800 000 gives >1000°), not an MCC-first LBS block. Frames
1 and 3 share the prefix `cb0385` with consecutive serials, so the field is slowly varying per device.
*Settled by:* a vendor 0x8C / FM08 / Lango PDF, or captures from two devices in known locations.
*Matters:* **medium.** Probably a cell block; we lose an LBS fallback for OBD dongles.

**Q13 — What is the trailing character of every 0x8C key (always `3`: `173`, `283`, `2D3`, `4A3`,
`503`)?** Not a length indicator — values run 1 to 17 characters with the same suffix.
*Settled by:* a vendor doc, or a capture from a device configured to report a different data type for
the same PID.
*Matters:* **low** for decode (strip it), **medium** for confidence that we are reading the right PID
space at all.

**Q14 — Is the 0x8C PID space the same as flespi's jt808 "OBD Data ID 0x05xx" space?** Seven IDs
corroborate (0x28, 0x2B, 0x2D, 0x30, 0x35, 0x36, 0x39); two refute it — flespi calls 0x47/0x48
relative/absolute throttle in percent, and the samples give 254.03 % and 1.03 % at 2450 rpm / 85 km/h,
then 0.15 % and 0.17 % at 1666 rpm / 58 km/h. A driving vehicle cannot have a 0.17 % throttle.
*Settled by:* a vendor doc for either flavour.
*Matters:* **medium.** Determines whether we can borrow flespi's labels for the unknown keys
(0x17, 0x22, 0x3A, 0x50) or must leave them raw.

**Q15 — What are 0x8C keys 0x17, 0x22, 0x3A and 0x50?** No mapping in any source. 0x17 and 0x22 carry
single-digit values (0 and 1) in both frames; 0x3A carries 1029 and 901; 0x50 is truncated to `0000`.
*Settled by:* a vendor doc, or a capture with deliberately varied vehicle state.
*Matters:* **low.** Store raw.

**Q16 — What is the unit of TLV module 0x002E (odometer)?** The only sample is 9000 — plausible as
9 km (metres), 90 km (0.01 km) or 9000 km. flespi labels the 0x70 equivalent `vehicle.mileage` in km
without stating the wire scaling. LL301's 0x22 mileage field has no unit at all.
*Settled by:* two captures from the same device separated by a **known driven distance**.
*Matters:* **high.** Odometer feeds mileage reports and, for some customers, invoicing. A 1000× error
is the kind that gets discovered by a customer, not by us.

**Q17 — Are the trailing 4 bytes on 0x12 length-0x23 frames an odometer or a temperature sensor?**
The reporter in traccar#5460 claims a wired temperature sensor; Traccar reads a 4-byte odometer. The
values `0x00000209` and `0x00000214` fit either (521/532 metres, or 5.21/5.32 °C at ÷100), and they
increment while the vehicle is **stationary**.
*Settled by:* the v1.9.0 section covering the temperature extension, or a log taken while heating the
sensor.
*Matters:* **high.** A stationary vehicle accumulating "mileage" is a billing and trust problem.

**Q18 — What divisor applies to 0x94 sub-type 0x1F ("temperature, 2 bytes big endian")?** No divisor
published, no sample. Its neighbour 0x1E is ÷10.
*Settled by:* a capture at a known ambient temperature.
*Matters:* **medium**, **high for cold-chain customers** — a number that looks like a temperature and
is off by a decade.

**Q19 — What is the humidity divisor in TLV module 0x007F (BLE tag)?** Battery (÷1000 V) and
temperature (÷10 °C) have divisors; humidity does not.
*Settled by:* a BLE tag reading at known humidity.
*Matters:* **medium.** Same shape as Q18.

**Q20 — What is the layout of TLV module 0x0030 (fuel sensor, 10 bytes)?** Samples
`000100b4000a00b402d0` and `000101680014016802d0`; flespi lists id/range/state/value for protocol 0x70
without giving the layout.
*Settled by:* a fuel-sensor-equipped 0x70 capture with a known tank reading.
*Matters:* **medium.** Fuel is a paid feature when it works.

**Q21 — What are TLV modules 0x003B (2 B), 0x003C (4 B, `01020001`), 0x1000 (1 B, always 0x01), and
0x002B (boot reason enum)?** Unmapped in every implementation.
*Settled by:* a vendor doc for the module space (none exists) or correlated captures.
*Matters:* **low.** Store raw; the TLV framing means they cost nothing to skip.

**Q22 — What is the scope of the 0x8E per-block checksum ("negated after all data is summed
together")?** Data0..Data7 only, or Type+Length+Data? **No 0x8E hex sample exists anywhere I
searched**, so the entire packet is spec-only and unvalidated.
*Settled by:* one real 0x8E capture.
*Matters:* **medium** now (nobody has the hardware), **high** if a customer buys a JC100-family unit —
we would be shipping an unvalidated CAN decoder.

**Q23 — How is the 0x8E type-0x23 steering angle encoded?** The doc's own example (`0x20 0x50` →
20.5°, `0xA0 0x50` → right 20.5°) reconciles only if those bytes are **BCD**, contradicting the hex
convention used in every other field of the same table and its own "low 7 bits = integer part"
sentence, which gives 32.80°. It also says "biggest angle is 40 degree", contradicting a 7-bit field.
*Settled by:* a capture with the wheel at a measured angle.
*Matters:* **low.** Nobody has asked for steering angle.

**Q24 — What do course-status bits 14 and 15 mean?** Every rank-1 doc shows them constant 0; Traccar
reads them as ignition-present/ignition-state and its author declined to name a source. In my corpus
b14 = 1 on 12 frames and b15 = 1 on 7, correlating with plausibly-moving vehicles — so they are not
always zero in the field.
*Settled by:* the protocol PDF for whichever variant introduced it, or a controlled test toggling
ignition on a device that sets b14.
*Matters:* **high** if we ever use them. **Do not.** Ignition comes from terminal-info bit 1 or the
ACC byte, and for an unmodelled device the attribute is absent, not `false`.

**Q25 — What should the server ACK when a device sends protocol 0x26 upstream?** LL301 defines 0x26 as
the server's reply to alarms, yet Traccar's corpus contains two device-originated 0x26 GPS+LBS+status
frames (length 0x25), and Traccar echoes 0x26 back. No document covers the upstream direction.
*Settled by:* a vendor doc listing 0x26 in a device-to-server protocol-number table.
*Matters:* **medium.** Echoing the received type is the safe default and is what R1 says anyway.

**Q26 — What is the GSM signal-strength scale, really?** All vendor docs define `0x00`–`0x04`. Real
frames contain `0x64` (100), and flespi publishes both `gsm.signal.dbm` and `gsm.signal.level`
(percentage), implying at least two encodings share the byte.
*Settled by:* a per-model doc, or paired SMS-status/GPRS captures from one device.
*Matters:* **low** for operations, **medium** for support ("the customer says signal is fine").

**Q27 — Is the multi-LBS RSSI byte a strength or a magnitude to negate?** LL301 §8 says `0x00` weakest
/ `0xFF` strongest and its own example descends 62, 49, 45, 24 outward from the serving cell. Traccar
does `int rssi = -readUnsignedByte()`. Both cannot be right.
*Settled by:* a device where the true serving-cell dBm is known independently.
*Matters:* **medium.** Wrong polarity inverts cell-geolocation weighting.

**Q28 — Which 0x94 sub-type carries the fuel-level sensor, and which field of `!AIOIL` is "the"
fuel?** LL301's index says 0x0C, its body says 0x0D, and the real frames carry it under 0x0D. The
field layout has nine fields in the doc and ten on the wire; the doc names field 2 as the sensor
output in cm, Traccar reports field 6.
*Settled by:* a calibrated fuel-sensor installation.
*Matters:* **medium.** Expose both fields, named; let the installer calibrate.

**Q29 — Is the login Terminal ID ever right-aligned differently** (a non-zero leading nibble, e.g. a
genuine 16-digit ID)? All seven corpus logins pad with a leading `0`.
*Settled by:* a capture from a device whose ID is not a 15-digit IMEI.
*Matters:* **medium.** Getting the IMEI wrong misroutes an entire device to the wrong tenant — and on
a multi-tenant platform that is the worst class of bug we have.

**Q30 — Does flespi's Concox changelog really contain a GPS-week-rollover fix?** The claim was relayed
to me through a summarisation and the raw thread would not load, so **treat the wording as
unconfirmed**. The underlying phenomenon is independently documented.
*Settled by:* loading <https://forum.flespi.com/d/64> directly.
*Matters:* **medium.** Determines whether we need an explicit rollover correction or just the
plausibility clamp (Trap 39).

## 10. Verdict

### 10.1 Is this implementable today without guessing?

**Yes — for a bounded subset, with the gates named below. No — for "GT06" as a category.**

The honest framing is that "GT06 support" is not one deliverable. Split it in three:

**Tier 1 — implementable today, no guessing required.** Envelope, CRC-16/X-25 with the exact span,
the CRC-arbitrated framer, login and the timezone word, the ACK contract, the 18-byte GPS block, the
course/status word, 2G and 4G LBS with the MCC bit-15 rule, protocol numbers
`0x01 0x10 0x11 0x12 0x13 0x15 0x16 0x19 0x1A 0x21 0x22 0x23 0x26 0x27 0x28 0x2A 0x2C 0x2E 0x8A 0x94
0x9B 0xA0 0xA1 0xA2 0xA4 0xA5 0xF1 0xFD`, the upload-mode/re-upload semantics, the alarm enum as a
**model-scoped dictionary**, and the 0x80 command channel with server-flag correlation.
Every byte offset in that list is VERIFIED against at least one vendor PDF **and** a frame I decoded.
That covers, by frame count, **roughly 85 % of the only corpus that exists** and every packet a
classic GT06/GT06N/GT07/LL301/VL0x actually emits in normal operation.

**Tier 2 — implementable behind an explicit per-device model, with a default-deny fallback.**
The 16 OEM dialects, the NT-family prefix, the SL4X/SEEWORLD/LW4G/TRX16i field maps, the battery
encodings, the 0x8C OBD channel, the TLV module space. These are decodable but not *inferable*: the
same bytes mean different things depending on a string a human typed. **The rule that makes this
safe is that an unmodelled device routes to the undecodable-records path rather than to a guess.**
We already have that path for Teltonika; GT06 must use it, and the operational cost is that
onboarding a new SKU requires one capture and one dictionary entry — not a code change.

**Tier 3 — not implementable today. Do not ship, do not estimate.**
`0x8E` (the only documented CAN packet — zero samples exist anywhere on the internet), `0x2D`
(delivery semantics defined by one ambiguous English sentence, zero frames), `0x65` DTC, media
transfer `0x35/0x36/0x41/0x8D`, `0x14/0x39/0x40/0x82/0xA9/0xB0/0xB2` (declared by Traccar, never
captured). Anything here that a customer needs is a **hardware-acquisition task**, not a coding task.

**Three prerequisites before any of it lands:**

1. **An ADR for the fix-validity divergence.** CLAUDE.md hard rule 6 (`satellites == 0 ||
   isNullIsland`) is wrong for this protocol in both directions — Trap 16 shows a 13-satellite fix in
   the right city that the device itself marks invalid. GT06 validity is
   `bit12 && !isNullIsland(lat, lon)`, with the satellite count kept as a quality metric.
   Per CLAUDE.md's own conflict procedure, that is an ADR, not a commit.
2. **A CRC guard in `tools/redact`.** Rewriting an IMEI in a GT06 capture invalidates the CRC. Our
   existing Teltonika redaction habit will manufacture Traccar's exact defect (Trap 25) inside our
   own golden corpus, where hard rule 9 then forbids us from fixing it.
3. **A per-device `model` and `firmware_build` in the registry**, populated from the 0xFD version
   string where the device sends one and from the operator otherwise. Without it, Tier 2 is
   guesswork wearing a dictionary.

**What I would *not* do:** import Traccar's corpus wholesale as golden fixtures. 28 of 183 frames
fail CRC and at least five are provably hand-edited vendor examples. Filter first, publish the
admitted-frame list as code (not as a percentage — the fact that four different percentages circulate
for the same corpus is proof the measurement was never reproducible), and classify the rejects into
*no CRC field* (0x17/0x69), *concatenations needing decomposition* (the 0xFD triple), *correctable
length* (TK200), and *genuinely corrupt*. Only the last category is unusable.

### 10.2 The riskiest byte

**The LBS-length byte** — the single byte immediately after the 18-byte GPS block in every
status-bearing packet (`0x16`, `0x26`, `0x27`, `0xA4`).

Why it, and not one of the more famous hazards:

* **The documented rule is provably wrong.** Both vendor PDFs and the upstream research bundle call
  it "self-inclusive: `1 + 2 + |MNC| + |LAC| + |CID|`". I measured every status-bearing frame in the
  corpus: the byte takes the values 0, 1, 8, 9, 10, 16 and 17, and **five CRC-valid frames declare 8**
  — a value that is structurally impossible under that rule, because MCC 2 + MNC 1 + LAC 2 + CID 3 is
  already 8 bytes of cell data before you count the length byte itself. **24 % of status frames
  disagree with the documentation.**
* **The error is exactly one byte, and it lands on the worst possible field.** Seek one byte early
  and the terminal-information byte — which carries **ignition (bit 1)**, the **alarm nibble
  (bits 3–5)**, **charging**, and the **immobiliser state (bit 7)** — is read from the low byte of
  the Cell ID.
* **Every symptom is plausible and silent.** On `787825161a…` the misread turns terminal-info `0x47`
  into `0x4B`, fabricating a VIBRATION alarm out of a Cell-ID byte. On `78782516160908…` ignition
  flips 1 → 0 and a trip silently ends. On `78782526160913…` the fix-valid bit flips 0 → 1 and an
  invalid position becomes trusted. Nothing throws. **No CRC fails** — the frame is intact; only our
  reading of it is wrong. Every value stays inside a storable range, so no validation catches it, and
  the first person to notice is a dispatcher being paged for an SOS that never happened.
* **There is no oracle.** The only corpus in existence has a 15 % CRC-failure rate, does not assert
  these fields, and the reference implementation quietly uses a *third* rule (`skip max(0, len − 9)`)
  that matches neither convention. You cannot test your way to the right answer from documentation;
  you can only test that you match observed firmware.

**The mitigation is three lines and a metric:** consume the cell fields by the type-driven widths of
§3.3, then `skip max(0, declared − 9)`, never use the byte as an absolute seek, and raise
`ingest_lbs_len_anomaly_total{model}` whenever the declared value is below 9 or above 17. Add the
range guard that makes the failure loud rather than plausible: **a decoded GSM value > 4, or a
voltage level > 6 on a level-encoding model, is a parse error, not a datum.**

**Runner-up, and it is close: the high byte of MCC.** Bit 15 selects a 1- or 2-byte MNC, the vendor
states in writing that the flag is `0` on already-shipped units and `1` on newly-shipped units of the
*same model*, and the resulting one-byte shift lands on the ACC/ignition byte — with the extra sting
that a length-keyed variant table then reclassifies the whole frame as a different vendor's dialect.
It is second only because the rule is documented correctly and repeated six times; the LBS-length
byte is the one where following the documentation is what breaks you.

## Appendix — suggested implementation order

1. CRC-16/X-25 + the span rule, with the seven reference vectors from §2.3. Nothing else works until
   this does.
2. The framer of §2.4, with the type-first ordering for `0x17/0x69`, and the property test that feeds
   every corpus frame at every split point.
3. Login, session binding, last-login-wins takeover, ACK builder (serial from `bytes[n-6..n-5]`),
   unknown-IMEI grace path.
4. The 18-byte GPS block + course/status word, with the four-hemisphere fixture set.
5. `fix_valid = bit12 && !isNullIsland(...)` — behind the ADR — and the Salvador fixture asserting
   zero trip-distance contribution.
6. LBS with the MCC bit-15 rule, type-driven LAC/CID widths, and the empirical LBS-length rule.
7. Status/heartbeat as **device-state events, never position rows**.
8. Upload-mode / re-upload parsed by offset from the end, and the pipeline rule that history does not
   raise real-time alerts.
9. Alarm and battery **dictionaries** (`source_url` per entry, CI-asserted completeness per model).
10. `0x94` sub-types, TLV modules (loop to the end, big-endian), `0xFD` version capture.
11. Everything else, per device model, behind default-deny.

Metrics to add at step 2 and never remove: `ingest_frame_resync_total`,
`ingest_crc_fail_total{protocol}`, `ingest_unknown_type_total{protocol}`,
`ingest_lbs_len_anomaly_total{model}`, `ingest_model_ambiguous_total{imei}`, plus the existing
`pipeline_lag_ms` and `stream_depth`.
